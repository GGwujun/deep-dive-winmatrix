# Agent 记忆系统的真实难题：不是 RAG，是遗忘

> 这是《WinMatrix 开发经验文集》第 3 篇。一提到"Agent 记忆"，大家第一反应都是"上 RAG"。但我们做下来发现，记忆系统真正的难题不是"怎么记起来"，而是"怎么别什么都记"、"怎么忘记该忘的"。代码来自 WinMatrix 后端真实实现。

"给 Agent 加个记忆系统"——这句话背后的默认动作，90% 的人会理解成"接个向量库，把对话历史塞进去，检索时做 RAG"。

这个理解不算错，但只覆盖了记忆系统 20% 的工作。真正难的、决定记忆系统好不好用的，是另外 80%：

- 一次对话里产生了几十轮交互，**哪些值得沉淀成长期记忆，哪些是噪音**？
- 项目记忆、会话记忆、跨会话记忆，**什么时候该用哪种**？
- 记忆越攒越多，**怎么不让无关记忆淹没真正重要的**？
- 同一个员工在不同项目里，记忆该**怎么隔离**？

这些问题的答案，比"接个向量库"复杂得多。这篇文章讲我们在 WinMatrix 里怎么解。

---

## 第一层认知：记忆不是一坨，是分层的

很多人把"记忆"当成一个平坦的池子——所有历史一股脑塞进去，检索时一把捞。这不对。

人的记忆是分层的：短期记忆（刚才说的话）、工作记忆（当前任务相关的）、长期记忆（沉淀的经验）。Agent 也该如此。WinMatrix 的记忆是三层结构：

```
┌─ 会话层 ─────────────────────────────┐
│  Redis conversation:{id}  (最近 50 条)│
│  PG   conversation_histories (永久)   │
└───────────────────────────────────────┘
                  │
                  ▼
┌─ 转录层 ─────────────────────────────┐
│  PG session_transcript                │
│  (含 tool_call / thinking trace)      │
└───────────────────────────────────────┘
          │ 防抖 10s 异步转化
          ▼
┌─ 长期索引层 ─────────────────────────┐
│  PG memory_chunks   (tsvector 全文)   │
│  ES dense_vector    (向量)            │
└───────────────────────────────────────┘
```

**会话层**：当前对话的即时上下文。Redis 里存最近 50 条（快），PG 里永久存（可靠）。Agent 响应时，主要看这一层。

**转录层**：完整的会话转录，包含每一次工具调用、每一段 thinking。这是"原始素材"——长期记忆从这里面提炼。

**长期索引层**：真正可检索的记忆库。双写 PG（全文检索，tsvector）和 ES（向量检索，dense_vector）。

三层各有各的用途、各有各的生命周期。**把它们混在一层，要么丢东西（只存 Redis），要么检索慢（全堆 PG），要么不可靠（只存 ES）。**

## 第二层认知：长期记忆不是手动存的，是自动转化的

很多人想象的记忆系统：Agent 觉得某句话重要，主动调一个"save_memory"工具存起来。

我们没这么做。原因有两个：

1. **Agent 不可靠**。让 LLM 自己判断"什么该记"，它会漏掉重要的、记住无关的。而且每次都要它做这个判断，浪费 token。
2. **开发者负担重**。每个技能都要记得"调用 save_memory"，忘了就丢数据。

我们的做法是**自动转化**——会话产生的转录，自动、异步地沉淀成长期记忆。负责这件事的叫 `TranscriptSyncManager`：

```
用户消息 → 会话层持久化
              ↓
        markDirty(conversationId)   ← 标记"这个会话有新内容了"
              ↓
        防抖 10 秒                   ← 攒一波，不一条一条处理
              ↓
        syncDirtyKeys()
              ↓
        formatTranscriptAsMarkdown() ← 把转录格式化成文本
              ↓
        indexContent(sessions)       ← 分块、向量化、入库
```

关键设计：

### 防抖，而不是实时

`markDirty` 之后不是立即同步，而是**防抖 10 秒**。为什么？因为一个用户可能连续发好几条消息，每条都触发一次同步是浪费。攒 10 秒，把这批消息一起处理，分摊了索引成本。

### 三种触发时机

```
事件驱动（增量，10s 防抖）  ← 主路径，实时性够、成本低
定时兜底（30 分钟全量）      ← 防事件驱动漏触发
启动同步（全量）             ← 重启后补齐
```

光有事件驱动不够——万一某个事件丢了，记忆就漏了。所以有 30 分钟的定时全量兜底。启动时还要全量同步一次，防止停机期间的状态丢失。**三层触发，任一层漏了都有其他层补上。**

### hash 去重，跳过没变的

每次同步时，先算内容 hash，和已存的比较：

```typescript
// infrastructure/memory/MemoryIndexManager.ts（第 370-384 行）
private async indexContentCore(pathKey, content, ...): Promise<number> {
  const contentHash = hashContent(content);
  const existing = await getMemoryFile(pathKey);
  if (existing && existing.hash === contentHash) {
    logger.debug(`[MemoryIndexManager] 内容未变更，跳过: ${pathKey}`);
    return 0;   // hash 相同，0 开销跳过
  }
  // ... 才做分块、入库
}
```

**没变的内容，零开销跳过。** 这是个简单但极其重要的优化——避免重复索引同样的内容，把成本压到只处理真正的增量。

## 第三层认知：检索不是一把捞，是分区的

记忆攒起来了，检索的时候怎么捞？最直觉的做法：把所有记忆做一次向量检索，取 top-K。

我们没那么做。因为记忆有不同的"相关度层级"，一把捞会把不相关的、跨场景的都混进来。

我们的检索分**三个区**：

```typescript
// agents/core/ai-kernel/context/adapters/MemoryContextBootstrap.ts（第 167-224 行）
// Zone 1: 当前会话 session
const zone1Results = await memoryService.search({
  query, projectId, conversationId,
  sources: ['session'], limit: 3, minScore: 0.25, hybrid: true,
});

// Zone 2: 项目 memory
const zone2Results = await memoryService.search({
  query, projectId, agentId,
  sources: ['memory'], limit: 3, minScore: 0.5, hybrid: true,
});

// Zone 3: 跨会话 session（仅当 Zone 1+2 不足 2 条时触发）
if (results.length < 2) {
  const zone3Results = await memoryService.search({
    query, projectId, excludeConversationId: conversationId,
    sources: ['session'], limit: 1, minScore: 0.8, hybrid: true,
  });
  // 跨会话记忆标记 ⚠️
}
```

三个区的关键差异：

| 区 | 来源 | 数量 | 阈值 | 含义 |
|----|------|------|------|------|
| Zone 1 | 当前会话 | 3 | 0.25 | 同一个对话里说过的话，最容易相关，阈值低 |
| Zone 2 | 项目记忆 | 3 | 0.5 | 本项目沉淀的经验，需要更相关才召回 |
| Zone 3 | 跨会话 | 1 | 0.8 | 别的对话里的内容，必须高度相关才召回 |

**三个细节决定了这套分区检索的质量：**

### 阈值递增

从 0.25 → 0.5 → 0.8，越往外相关性要求越高。**因为越往外的记忆，"张冠李戴"的风险越大。** 当前会话里的话，多半是相关的；但别的对话里的一句话，即使向量相似，也可能是在完全不同的语境下说的。阈值递增是对这种风险的防范。

### Zone 3 只在前两区不够时触发

`if (results.length < 2)` —— 只有 Zone 1 和 Zone 2 召回不足时，才去翻跨会话记忆。这是**降级检索**：能用近的、确定相关的，就别用远的、可能跑题的。绝大多数情况下 Zone 1+2 就够了，Zone 3 是个"实在没辙了才翻"的兜底。

### 跨会话记忆要标记

Zone 3 召回的记忆，会被打上 `isCrossConversation: true` 标记，并加 ⚠️ 提示。为什么？因为**Agent 必须知道"这条记忆是别的对话里的"，使用时要更谨慎**。一个不加区分、把跨会话记忆当成本会话上下文用的 Agent，很容易说出"你上次不是说……"这种让用户摸不着头脑的话。

## 第四层认知：记忆是自动注入的，不是 Agent 主动找的

很多 Agent 系统的设计是：给 Agent 一个 `memory_search` 工具，它觉得需要就去搜。

我们的主路径不是这样。**记忆是自动注入的**——每轮构造系统提示词前，系统自动检索相关记忆，塞进上下文，Agent 看到的提示词里已经包含了记忆。

```typescript
// MemoryContextBootstrap.ts（第 370 行）
export async function injectLongTermMemory(input: InjectLongTermMemoryInput): Promise<...> {
  // 每轮构造系统提示前自动检索
}
```

注入的记忆还带**类型标签**：

```
[decision] 上次决定用 React 而不是 Vue
[finding]  接口 X 的鉴权用的是 JWT
[preference] 用户偏好简洁的回答
[constraint] 不能访问生产数据库
[info] 项目部署在阿里云
```

这些标签让记忆是**结构化、可读**的，而不是一坨模糊的文本。

为什么自动注入优于 Agent 主动搜？

1. **Agent 不会"忘了搜"**。主动搜索依赖 Agent 判断"我需不需要查记忆"，而这个判断本身不可靠。
2. **省 token**。自动注入只在每轮做一次精确的检索，而不是让 Agent 反复调 search 工具。
3. **可控**。注入哪些记忆、注入多少，由系统决定，可观测、可调。

当然，我们也保留了 `memory_search` 工具（`MemorySearchTool`），作为 Agent 主动深挖的手段。但那是补充，主路径是自动注入。

## 第五层认知：记忆要隔离，不能串味

一个员工（比如阿码）同时在 A 项目和 B 项目工作。A 项目里记的"用 React"，不能影响 B 项目的决策。否则就乱套了。

我们的隔离是**两个维度**：

**员工维度**：`memory_chunks.agent_id` 按员工隔离。阿码的记忆和阿宁的记忆不串。这和"一 Role 对应一数字员工"的模型一致——每个员工有自己的记忆空间。

**项目维度**：默认按 `projectId` 过滤。项目 A 的记忆只在项目 A 的上下文里召回。**综合区**（`projectId='_general'`，或项目名是"综合区"）是例外——它不传 projectId，检索全库，作为跨项目的通用记忆。

这种双维隔离，保证了"阿码在 A 项目学到的经验，帮助的是 A 项目的阿码，而不是 B 项目的阿宁"。**没有隔离的记忆系统，会把不同场景的经验搅成一锅粥。**

## 第六层认知：上下文可判定性——Agent 这一轮到底看到了什么

最后一个容易被忽视的点。

Agent 的回答，取决于它"看到"了什么。但如果出错了——Agent 答非所问、引用了奇怪的东西——你怎么知道它当时看到了哪些记忆？

我们的做法是**每一轮注入都记录可观测事件**：

```
llm_context_snapshot 事件：
  memoryInjectedCount: 3        ← 注入了 3 条记忆
  injectedMemoryPaths: [...]    ← 具体是哪几条
  chatHistoryLength: 10         ← 对话历史长度
```

而且每轮注入有明确的**上限**：

- 相关记忆 top-k = 5
- 对话历史 `getRecentMemory(10)`
- 工作上下文 `getWorkingContext(10)`

这些上限不是随便写的——它们保证了**每一轮注入到 LLM 的内容是有限的、确定的、可事后还原的**。事后排查"Agent 为什么这么答"，你能精确还原它当轮看到了什么。

**这叫"上下文可判定性"**。一个记忆系统如果不能回答"当时 LLM 看到了什么"，它就是个黑盒，出问题时只能猜。把每轮注入做成可观测、有上限、可回放，是记忆系统从"能用"到"可维护"的分水岭。

## 关于"遗忘"

回到文章标题——遗忘。

WinMatrix 的记忆系统里，"遗忘"主要体现在几个地方：

1. **会话层 Redis 只存最近 50 条**——更早的会话上下文，"忘"掉（转由长期记忆层按需召回）。
2. **三区阈值递增**——不够相关的记忆，"想不起来"（不召回）。
3. **Zone 3 只在前两区不够时触发**——跨会话的、可能跑题的，"懒得想"（降级检索）。
4. **每轮注入有上限**——即使记得很多，一次也只"想起" top-K。

这些机制合起来，构成了一个"主动遗忘"的记忆系统。**它的目标不是"记住一切"，而是"在恰当的时候，想起恰当的事"。**

记住一切是容易的（加存储就行），难的是**克制**——只在该记的时候记，只在该想起的时候想起，把无关的、过时的、跨场景的记忆挡在上下文之外。这才是 Agent 记忆系统的真正难题。

## 给后来者的几条总结

1. **记忆是分层的，不是一坨**。会话层、转录层、长期索引层，各有用途和生命周期。
2. **长期记忆靠自动转化，不靠 Agent 主动存**。Agent 判断"什么该记"不可靠，自动 + 异步 + 防抖才是正解。
3. **同步要三层触发**：事件驱动（实时）+ 定时兜底（防漏）+ 启动全量（防丢）。hash 去重跳过未变更。
4. **检索分区，别一把捞**。当前会话、项目记忆、跨会话三层，阈值递增、降级触发、跨会话要标记。
5. **记忆自动注入优于 Agent 主动搜**。主路径自动注入带类型标签，主动 search 只是补充。
6. **记忆双维隔离**：员工维（agent_id）+ 项目维（projectId）。综合区是跨项目的例外。
7. **上下文可判定性**：每轮注入记录 snapshot、设明确上限。事后能还原"Agent 当时看到了什么"。
8. **真正的难题是遗忘，不是记住**。克制地记、克制地想起，比"记住一切"难得多。

一个扎实的记忆系统，目标不是让 Agent 变成"过目不忘的复读机"，而是让它"在恰当的语境里，想起恰当的事"。这背后的工程，远不止"接个向量库"那么简单。
