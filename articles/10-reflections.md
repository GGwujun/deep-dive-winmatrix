# 从"AI 助手"到"AI 员工"：我们做对和做错的几件事

> 这是《WinMatrix 开发经验文集》最后一篇。前面九篇都在讲"怎么做"，这一篇讲"为什么这么做"，以及回头看，哪些选择是对的、哪些是走过弯路的。如果你也在做一个企业级 AI 产品，希望这些得失能帮你少绕几圈。

WinMatrix（翠花）的核心定位是一句话：**让 AI 不只是工具，而是团队的一员**。

这不是一句营销话术，它是一个很强的工程约束。一旦你认真对待"AI 是员工"这件事，整个系统的架构、数据模型、交互方式都会被推着往一个特定方向走。这一篇，我们就聊聊被这个定位推出来的几个关键决策——以及代价。

---

## 做对的第一件事：把"角色"作为一等公民

很多 AI 产品的架构是"一个万能 Agent + 一堆工具"。听起来灵活，实际跑起来你会发现：用户不知道这个 Agent 到底擅长什么，Agent 自己也常常在"该用哪个工具""该用什么风格回答"上反复横跳。

WinMatrix 的选择是反过来的——**先有角色，再有 Agent**。我们定义了明确的数字员工：

- **大福**（项目总指挥 orchestrator）：负责项目启动、拆解、协调
- **阿宁**（事项管理者 process_manager）：日会、周报、进度跟踪
- **小品**（产品管理人员）：PRD、需求分析
- **阿码**（架构师 tech_manager）：技术方案、代码评审
- 小质（质量管理）、大维（SRE）、Architector（系统设计师）……

每个角色绑定自己的技能集、工具权限、提示词模板、记忆空间。数据模型上，`DigitalEmployee` 和 `Role` 一一对应，不是"一个模型套不同 prompt"，而是"一个完整的人格化实体"。

### 为什么这样做是对的

- **可预期性大幅提升**。用户找大福，就知道是来启动项目的；找阿码，就是技术问题。角色的边界就是用户预期的边界。
- **权限收敛天然成立**。质量管理员不需要部署权限，产品经理不需要写代码权限。角色绑定工具，比"全局工具池 + 运行时判断"安全得多。
- **协作有了语义**。"让阿码评审小品写的 PRD"是一句有意义的话，因为阿码和小品都有明确的能力定义。

### 代价

- **灵活性下降**。一个跨领域的请求，可能需要在多个角色间路由。我们用"智能路由 + 渐进式决策引擎"来缓解，但这套机制本身不简单。
- **角色膨胀的风险**。业务变化时，是新增角色还是扩展现有角色的技能？这是个持续的产品判断，没有银弹。

> 给后来者的建议：**如果你做的是 toB、流程明确的产品，"角色优先"是对的**。如果是 toC、开放域的助手，可能"一个大脑 + 工具"更合适。别反过来。

## 做对的第二件事：渐进式决策，而不是"一锤子 LLM 调用"

一个用户消息进来，怎么决定让哪个员工、用哪些技能、走什么流程？

最直觉的答案是"丢给 LLM，让它规划"。我们一开始也这么想过。但很快发现三个问题：

1. **贵**。每条消息都过一遍 LLM 规划，token 成本和延迟都顶不住。
2. **不稳**。同样的输入，LLM 可能规划出不同的路径，调试和回归测试噩梦。
3. **没必要**。大量请求其实是模式化的——"生成日会"就该走日会技能，根本不需要 LLM 来"决定"。

所以我们做了**渐进式决策引擎**：一个分阶段的管线，从最便宜、最确定的阶段开始，逐渐升级到昂贵的 LLM 规划。大致是：

```
精确路由（关键词/意图匹配，零 LLM 成本）
   ↓ 没命中
轻量路由（小模型/embedding 判定，低成本）
   ↓ 不确定
LLM 规划（完整决策，高成本但兜底）
   ↓ 还要确认
承诺推导 + 流水线钩子（校验、约束、最终落地）
```

### 为什么这样做是对的

- **80% 以上的请求在前两阶段就被解决了**，根本到不了昂贵的 LLM 规划。成本和延迟都压下来了。
- **确定性的部分用确定性手段**。模式匹配比 LLM 稳，该用就用。
- **LLM 是兜底，不是默认**。真正模糊的、需要推理的，才交给它。这样 LLM 的"不稳定性"被限制在一个可控的尾部。

### 这个设计的灵魂：L1/L2/L3 边界

我们把"一个技能能不能执行"也做了分层检查（这就是技能的 L1/L2/L3 readiness）：

- **L1**：技能存在吗、启用了吗？（最便宜，决策阶段就过滤）
- **L2**：依赖的输入满足吗？（组装阶段检查）
- **L3**：运行时资源就绪吗？（执行前最后一关）

核心思想是**尽早失败**——别让一个注定失败的执行跑到一半才崩。每一层都比下一层便宜，越早过滤掉不可用的路径，整体成本越低。

> 给后来者的建议：**任何"用 LLM 做决策"的地方，先问一句：这件事能不能用更便宜的确定性手段先过滤掉大部分？** 能，就分阶段。LLM 是工程师手里的最后一张牌，不是第一张。

## 做对的第三件事：技能（Skill）= 提示词模板 + Agent 封装 + 契约

"技能"是 WinMatrix 里我最喜欢的一个抽象。一个技能（写 PRD、做代码评审、生成日报）不是一个函数，也不是一段 prompt，而是：

- 一段**提示词模板**（告诉 LLM 怎么干）
- 一个 **Agent 封装**（决定用什么模型、什么工具、什么记忆）
- 一组**契约**（`provides` 我产出什么 / `consumes` 我依赖什么）

契约机制是关键。它让技能之间可以自动串联：

- `prd_writing` 技能 `provides: [prd_document]`
- `tech_solution` 技能 `consumes: [prd_document]`

把这两个技能放进一个流程编排，系统就知道：技术方案这一步要等 PRD 产出，PRD 的产出自动注入技术方案的输入。不需要人去写胶水代码。

### 为什么这样做是对的

- **复用性**。一个技能是自包含的，可以在不同流程、不同角色间复用。
- **可组合**。契约让技能像积木一样拼装，多步工作流的串联变成了数据流问题。
- **可治理**。技能是独立的治理单元——可以加白名单、要审批、做版本管理。这对企业落地是刚需。

### 代价 / 走过的弯路

- **早期我们把技能做成了"bundled"的硬编码包**。后来发现技能要演进、要热更新、要从市场安装，bundled 路径走不通，最终重构为 artifact-store（技能产物存储）模式，bundled 被标为 deprecated。这是一次代价不小的迁移。
- **Schema 漂移是真问题**。技能定义会演进，旧技能工件和新 Schema 会不一致。我们专门做了启动时的 Schema 漂移检测来告警。

> 给后来者的建议：**如果你的"技能/能力"需要动态加载、版本管理、热更新，从一开始就用"产物 + 存储 + 哈希校验"的思路，别走硬编码 bundled。** 后期迁移的成本远大于前期的设计成本。

## 做对的第四件事：可观测性必须是一等公民，不是事后补的

做 Agent 平台，调试一次"跑飞了"的执行，比写它还痛苦。一个 Turn 里可能有路由、决策、多次工具调用、多轮 LLM 调用，散落在日志里根本拼不出全貌。

我们最终收敛到**统一执行追踪（ExecutionSpan）**：每一次执行——不管是 Agent run、Turn、工具调用、还是 LLM 调用——都是一棵 span 树上的一个节点，有 parent、有 duration、有 status、有结构化的输入输出。

`SELECT span_kind, started_at, executor_employee_name, status FROM execution_span WHERE conversation_id = '...' ORDER BY started_at;`

一句 SQL，一次对话里"谁、什么时候、做了什么、成功没"就全出来了。

### 为什么这样做是对的

- **从"翻日志"变成"查树"**。结构化的 span 树比 grep 日志高一个维度。
- **LLM 调用天然可观测**。LLM span 带模型、token 数、延迟、prompt 摘要，成本归因变得可行。
- **取代散落的日志表**。我们甚至把旧的 `agent_execution_log` 退役了，统一用 span——单一事实来源（SSOT）的价值。

> 给后来者的建议：**在写第一个 Agent 之前就把 span 追踪搭好**。等到生产事故来了再补，你要面对的是几百万行无法关联的日志，和一堆已经写死 `console.log` 的代码。

## 做错 / 后悔的几件事

公平起见，也说说走错的路。

**1. 早期对"向后兼容"太执着。** 功能重构时总想保留旧路径，结果系统里长期挂着两套并行的实现，维护成本翻倍。后来定了规矩：功能重构默认不需要向后兼容，除非明确说明。包袱轻了，迭代快了。

**2. 文档散落、SSOT 不清晰。** 一段时间里，架构真源散在 CLAUDE.md、AGENTS.md、docs/规划/、各种 .md 里，且彼此可能滞后。后来明确"架构 SSOT 在一处，其他都是链接"，才慢慢收敛。文档治理和代码治理一样重要。

**3. 数字口径不一致。** "几个模型""几个技能""几层记忆"这种数字，不同时期写的文档对不上（这本书的早期版本也有这毛病，后来逐章核对源码修正）。数字看起来是小事，但它暴露的是"有没有人真的在维护事实"。

**4. 低估了"协作"的复杂度。** 多个 AI 员工协作（谁主导、谁配合、消息怎么派发、结果怎么汇总）比单 Agent 难一个数量级。我们为此做了协作会话、流程编排、角色收件箱（role inbox）一整套机制，投入远超预期。如果你只做单 Agent，恭喜你省了一大半的复杂度。

## 给后来者的几条总结

1. **定位决定架构**。"AI 是工具"和"AI 是员工"是两个完全不同的产品，别用同一个架构硬套。
2. **确定性优先于 LLM**。能用规则、路由、模式匹配解决的，别上 LLM。LLM 是兜底。
3. **尽早失败，分层检查**。L1/L2/L3 的思路适用于一切"要不要执行"的判断。
4. **抽象要带契约**。技能、工具、流程，凡是想复用和组合的，都要有明确的输入输出契约。
5. **可观测性先行**。span 树是 Agent 时代的"日志"，第一天就搭好。
6. **横切关注点收口**。连接恢复、鉴权、限流、追踪——用 Proxy/中间件统一处理，别靠纪律。
7. **动态能力用产物模式**。需要热更新、版本、市场分发的东西，别硬编码。
8. **文档要有单一真源**。散落的文档比没有文档更危险，因为它制造"我知道"的幻觉。

## 写在最后

做 AI 平台这一年多，我最深的感受是：**模型在飞速进步，但工程问题几乎没变。**

新的模型让"能做什么"的天花板不断抬高，但真正决定一个产品能不能在企业里活下来的，还是那些老掉牙的工程基本功——分层、契约、可观测性、错误恢复、文档治理、向后兼容的策略。

模型是引擎，工程是底盘和转向。引擎再猛，底盘散架，车还是开不到终点。

希望这十篇文章，能帮你在"AI 员工"这条路上，把底盘做扎实一点。
