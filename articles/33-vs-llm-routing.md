# 渐进式决策 vs 纯 LLM 路由：为什么我们不学 AutoGPT

> 这是《WinMatrix 开发经验文集》第 33 篇，"行业对比与方法论"系列第三篇。一个用户消息进来，该让哪个 Agent 处理、走什么流程？这个"决策"是 Agent 系统的入口。业界有两种典型哲学：让 LLM 全权决定（纯 LLM 路由），或者用确定性规则优先、LLM 兜底（渐进式决策）。这篇聊我们为什么选后者，以及前者的适用场景。

做 Agent 系统，有一个决策点贯穿始终——**怎么决定下一步干什么**。

这个问题有两种极端的答法。

一种是**全 LLM 图**：把所有可能的状态、动作、工具都描述给 LLM，让它自己决定下一步。业界有一批知名框架走这条路——以"让 Agent 自主规划和执行"为核心，用一个（或几个）LLM 调用构成动态的、图状的决策流。这条路最诱人的地方是"通用性"——理论上，只要描述得够清楚，LLM 能处理任何任务。

另一种是**显式图编排**：把工作流画成一张确定的图（节点 + 边），每一步做什么、下一步去哪都写死，LLM 只在需要"理解"的节点里出现。这条路最诱人的地方是"确定性"——流程可预测、可调试、可回归测试。

WinMatrix 选的是介于两者之间的**渐进式决策**：确定性规则优先，多信号融合，LLM 作为兜底。这篇就把三种思路摆开，讲清楚各自适合什么，以及为什么我们不走"全 LLM 图"这条路。

---

## 先把三种思路画清楚

**全 LLM 图（以"自主 Agent"为代表）**：

```
   用户输入
      ↓
   ┌──────────────┐
   │  LLM（大脑）   │ ← 看到所有可选动作、历史、状态
   │  自主规划      │
   └──────┬───────┘
          ↓ 决定一个动作
   ┌──────────────┐
   │  执行动作     │ → 改变状态
   └──────┬───────┘
          ↓ 观察结果
   ┌──────────────┐
   │  LLM 再决策   │ ← 循环，直到 LLM 说"完成"
   └──────────────┘
```

特征：LLM 是唯一的决策者。每一步都问 LLM"接下来干什么"，LLM 根据当前状态和历史决定动作，执行后再问 LLM，循环往复。流程是运行时动态生成的，不是预先定义的。思路是"reAct"（Reason + Act）的极致形态。

**显式图编排（以"流程引擎"为代表）**：

```
   用户输入
      ↓
   ┌────────┐    ┌────────┐    ┌────────┐    ┌────────┐
   │ 节点 A  │ →  │ 节点 B  │ →  │ 节点 C  │ →  │ 节点 D  │
   │ 写 PRD  │    │ 评审    │    │ 技术方案│    │ 测试    │
   └────────┘    └────────┘    └────────┘    └────────┘
                  ↑ LLM 只在需要"理解"的节点出现
```

特征：流程是一张确定的图。每一步做什么、下一步去哪，都在图里写死。LLM 只在"需要理解自然语言"的节点里被调用（比如"写 PRD"这个节点内部用 LLM 生成 PRD），但"从写 PRD 到评审"这个流转是确定的，不需要 LLM 决定。

**渐进式决策（WinMatrix 的做法）**：

```
   用户输入
      ↓
   Stage 1: 精确路由（零 LLM）—— 能命中就短路
      ↓ 没命中
   Stage 2: 融合路由（规则 + 语义打分）—— 能定就定
      ↓ 不确定
   Stage 3: 快速接受（语义缓存）—— 命中就复用
      ↓ 没命中
   Stage 4: LLM 规划（完整决策）—— 兜底
      ↓
   Stage 5: 承诺派生（校验 LLM 输出）—— 只放行合法的
```

特征：决策是一条分阶段的管线，从最便宜、最确定的阶段开始，逐渐升级到昂贵的 LLM。每一阶段都能"短路"——能确定答案就直接返回，不往下走。LLM 是最后的兜底，不是第一选择。

---

## 第一个对比点：成本

三种思路最直观的差异是 LLM 调用成本。

**全 LLM 图**的决策成本最高。因为每一步都问 LLM，一个任务跑 10 步就是 10 次 LLM 调用——而且每次都要带上完整的历史和可用动作列表，prompt 越跑越长，token 成本随步数线性甚至超线性增长。更要命的是，很多"决策"其实是模式化的——"生成日会"就该走日会技能，根本不需要 LLM 来"决定"——但全 LLM 图不区分模式化任务和探索性任务，一律丢给 LLM，白白浪费。

**显式图编排**的决策成本最低。因为流程是确定的，"下一步去哪"不需要 LLM 决定，LLM 只在具体节点内部出现。但它的代价是灵活性——图必须预先画好，遇到图没覆盖的场景就卡住。

**渐进式决策**的成本介于两者之间，但更接近"显式图"。因为 80% 以上的请求在前两个阶段（确定性规则）就被解决了，根本到不了 LLM。我们在决策管线里埋了 hook（第 2 篇），能看到每个阶段的命中率——实测下来，真正需要 LLM 规划的请求是长尾，可能不到 20%。

```
三种思路的成本结构（定性）：
  全 LLM 图：     每步都 LLM，成本随步数线性增长
  显式图编排：    只在节点内 LLM，成本最低但僵硬
  渐进式决策：    80% 确定性短路 + 20% LLM 兜底，成本可控且灵活
```

这里有个关键的工程洞察：**绝大多数企业场景的请求是模式化的**。"写 PRD""生成日会""做代码评审"这些高频请求，背后都是固定的技能，根本不需要 LLM 来"决定走哪条路"。LLM 真正的价值在于处理那 20% 的、从未见过的、模糊的、需要推理的请求。把 LLM 用在它不擅长（确定性决策）且昂贵的地方，是全 LLM 图最大的浪费。

---

## 第二个对比点：稳定性与可调试性

成本之外，稳定性是企业场景的另一个硬指标。

**全 LLM 图**最大的问题是**不稳定**。同样的输入，LLM 今天可能走 A 路径，明天走 B 路径。这在 demo 里看起来很酷（"看，AI 能自己探索"），但在生产里是噩梦：

- **调试难**。用户反馈"这次回答不对"，你复现不了——因为 LLM 这次可能走完全不同的路径，错误无法重现。
- **回归测试难**。你没法给一个"LLM 自主决策"的系统写确定性的回归测试，因为输出不可重复。
- **用户预期管理难**。用户不知道同样的输入会得到什么，信任建立不起来。

**显式图编排**最稳定——流程确定，输入相同输出必然相同（节点内部的 LLM 输出可能有波动，但流转逻辑是确定的）。可调试、可测试、用户可预期。但它的代价是**僵硬**——遇到图没画到的场景就报错或卡住，没有"见机行事"的能力。

**渐进式决策**的稳定性是分层的：

- Stage 1-3（确定性规则）：完全稳定，可复现，可测试。
- Stage 4（LLM 规划）：有波动，但这种波动被限制在"20% 的长尾请求"里，且 Stage 5 的承诺派生会校验 LLM 输出的合法性——**LLM 可以"建议"，但系统只"承诺"它校验通过的**。

```
稳定性的分层（WinMatrix）：
  ┌─────────────────────────────┐
  │ Stage 4: LLM 规划（有波动）  │  ← 只在长尾请求出现
  └─────────────────────────────┘
  ┌─────────────────────────────┐
  │ Stage 5: 承诺派生（校验层）  │  ← LLM 输出需校验才生效
  └─────────────────────────────┘
  ┌─────────────────────────────┐
  │ Stage 1-3: 确定性（完全稳定）│  ← 80%+ 请求死在这里
  └─────────────────────────────┘
```

这种分层的好处是：**LLM 的"不稳定性"被限制在一个可控的尾部**。大部分请求走确定性路径，完全稳定；少部分走 LLM，但有校验兜底。整个系统的稳定性下限被确定性阶段托住了，不会因为 LLM 偶尔抽风就全线崩。

### 可调试性：候选 → 计划 → 承诺三段分离

渐进式决策还有一个全 LLM 图很难做到的事——**可调试性**。我们把决策拆成了三个清晰的阶段产物（第 2 篇）：

1. **候选（Candidate）**：Stage 2 产出的"可能适用的技能/员工"列表，带证据（融合分数、检索证据）。
2. **计划（Plan）**：Stage 4 LLM 产出的"打算怎么执行"的 patch，软的，待校验。
3. **承诺（Commitment）**：Stage 5 校验通过的、真正可执行的 plan，硬的。

这个分离的价值在于**问题能定位到独立的环节**：

- 候选错了？调 FusionRouter 的规则和阈值。
- 计划错了？调 LLM 的 prompt 和上下文。
- 承诺错了？调校验规则和 stepBindings。

而全 LLM 图里，决策是一个混沌的整体——"为什么走这条路径"这个问题，答案是"LLM 这么决定的"，没有可调节的独立环节。

---

## 第三个对比点：对"新场景"的适应力

成本和稳定性之外，还有一个维度——**对新场景的适应力**。

**全 LLM 图**在这方面最强。因为它不预设流程，遇到从没见过的任务，LLM 可以自己尝试拆解和规划。这是"自主 Agent"最吸引人的地方——理论上它能处理任意任务，包括设计者没预见到的。

**显式图编排**在这方面最弱。图是预先画好的，遇到图没覆盖的场景，要么报错要么卡住。每加一种新场景，都得人工修改图（加节点、加边），不能自适应。

**渐进式决策**的适应力介于两者之间，且**分层适应**：

- 新场景如果和已有规则相似，会在 Stage 2 的融合路由里被"近似命中"——因为它用的是多信号融合打分（正则 + 意图词 + 语义锚点），不是死匹配。`route_rule` 表里的 `semanticAnchors` 和 `semanticThreshold`（默认 0.85）让相似的新输入有机会命中已有规则。
- 新场景如果完全没见过，会落到 Stage 4 的 LLM 规划——这就是 LLM 作为兜底的价值，它处理那"从没见过的 20%"。

```
渐进式决策的分层适应力：
  Stage 2 融合路由：相似场景"近似命中"（语义容错）
  Stage 4 LLM 规划：全新场景"自主规划"（LLM 兜底）
```

这种分层适应的关键是 `route_rule` 的 shadow 机制（第 30 篇讲过）——新规则可以先设成 shadow 灰度观察，验证命中率后再转 active。这让"给系统加新场景"变成了一个**可控的、渐进的过程**，而不是全 LLM 图那种"扔给 LLM 碰运气"。

## 业界"全 LLM 图"思路的问题出在哪

讲完了三个对比点，聊聊为什么我们不学业界那批"全 LLM 图"框架。不是它们错，而是它们的核心假设在企业场景里不成立。

**假设一：LLM 足够聪明，能做所有决策。** 这个假设在 demo 里成立（简单任务 LLM 看起来决策得很好），但在企业生产里不成立。企业任务的"正确决策"往往涉及业务规则（"这种合同要走法务评审"）、权限约束（"这个员工不能直接部署"）、历史上下文（"这个项目之前否决过类似方案"）——这些光靠 LLM 的通用推理把握不住，得靠规则和系统状态。

**假设二：LLM 调用便宜到可以随便用。** 这个假设在每条消息独立看时成立（一次 LLM 调用几毛钱），但在高频生产系统里不成立。一天几万条消息，每条都过完整 LLM 决策，月账单能吓死人。第 29 篇讲过，成本治理的前提是"大部分请求不该用 LLM"。

**假设三：不稳定性可以靠更好的 prompt 解决。** 这个假设是乐观的幻觉。prompt 调得再好，LLM 的输出依然有概率性波动。在企业场景里，"99% 对、1% 错"是不可接受的——那 1% 的错误如果涉及权限或资金，就是生产事故。确定性规则能做到 100% 对（因为它是写死的），该用就用。

**假设四：动态流程比固定流程更强大。** 这个假设在开放域成立（探索性任务确实需要动态流程），但在企业流程场景里不成立。企业的工作流（从需求到交付）往往是固定的、有制度约束的，"动态"反而是坏事——它意味着不可控、不可审计、不可追责。

**所以我们的态度是：LLM 是工程师手里的最后一张牌，不是第一张。** 能用规则、路由、模式匹配解决的，别上 LLM。LLM 只在最必要的时候登场，而且登场了也要校验它的输出（Stage 5 承诺派生）。这种"把 LLM 当作需要监督的手段"的态度，是 Agent 系统能在企业里活下来的前提。

## 全 LLM 图思路什么时候仍然有价值

公平起见，也要说清楚全 LLM 图思路在什么场景下仍然有价值——不是一无是处。

**全 LLM 图适合的场景**：

- 开放域、探索性、单次性的任务。比如"帮我研究一下这个新领域"——没有固定流程，需要 LLM 自主探索。
- 容错率高、不要求确定性的场景。比如个人助手、创意辅助——错了重来成本低。
- 任务结构无法预先穷举的场景。比如处理自然语言的任意指令——你没法预先画出所有可能的流程图。
- demo、原型、研究性项目。目的是探索能力边界，不是稳定生产。

**渐进式决策适合的场景**：

- 企业流程、高频、模式化的任务。绝大多数请求有固定模式，不需要 LLM 决策。
- 对稳定性、可调试性、可回归测试有硬要求的场景。
- 成本敏感、需要控制 LLM 调用量的场景。
- 有明确业务规则和权限约束，需要确定性执行的场景。

**判断标准**：如果你的系统主要处理"结构化、模式化、有规则"的请求（企业场景的常态），用渐进式决策；如果你的系统主要处理"非结构化、探索性、无规则"的请求（开放域 AI 助手的常态），全 LLM 图更合适。大多数企业 AI 落地属于前者，所以渐进式决策是更稳的默认选择。

## 一个容易被忽略的点：显式图编排并不和渐进式决策冲突

讲到这里，有一个容易混淆的点要澄清——**显式图编排（流程引擎）和渐进式决策不冲突，它们是互补的**。

WinMatrix 里有完整的流程编排体系（第 20 章）：flow_template（草稿）→ flow_template_version（不可变发布版）→ flow_run（实例），三层模型。这是"显式图编排"的典型实现——把多步工作流画成确定的图，一步步流转。

但这个流程编排不是替代决策引擎的。它们的分工是：

- **决策引擎**决定"这条消息要不要触发一个流程、触发哪个流程"。
- **流程编排**决定"流程触发后，内部怎么一步步流转"。

```
决策引擎（渐进式）         流程编排（显式图）
     ↓                          ↓
"这条消息走 prd 流程"   →   "prd 流程：写 PRD → 评审 → 技术方案"
```

用户说"帮我从需求到技术方案走一遍"，决策引擎（可能 Stage 1 的 ExplicitFlowOrchestration 短路，见第 2 篇）识别出这是一个显式多步流程，直接编译成 flow_run；之后流程内部按确定的图流转，不需要再每步问决策引擎。**渐进式决策管"入口判断"，显式图编排管"内部流转"，两者各管一段。**

这是 WinMatrix 区别于纯"全 LLM 图"或纯"显式图"的地方——我们不非此即彼，而是**把确定性用在确定性最强的环节（流程流转），把 LLM 用在 LLM 最有价值的环节（入口决策的兜底 + 节点内的自然语言处理）**。这种"分层使用确定性手段和 LLM"的态度，是渐进式决策的精髓。

## 给后来者的几条总结

1. **三种思路不是对错，是取舍**。全 LLM 图灵活但不稳；显式图编排稳定但僵硬；渐进式决策折中，确定性与灵活性兼得。
2. **成本的洞察：大部分企业请求是模式化的**。80%+ 不需要 LLM 决策。把 LLM 用在确定性决策上是全 LLM 图最大的浪费。
3. **稳定性是分层托底的**。确定性阶段（Stage 1-3）完全稳定，托住下限；LLM 阶段（Stage 4）有波动但有校验（Stage 5）兜底。LLM 的不稳定性被限制在可控尾部。
4. **可调试性靠"三段分离"**。候选 → 计划 → 承诺，每段独立可调。全 LLM 图的决策是混沌整体，没法定位环节。
5. **适应力是分层的**。Stage 2 融合路由对相似场景语义容错，Stage 4 LLM 对全新场景兜底。shadow → active 让加新场景可控。
6. **LLM 是最后一张牌，不是第一张**。能用规则、路由、模式匹配解决的别上 LLM。LLM 登场了也要校验输出。这是企业落地的前提。
7. **全 LLM 图适合开放域探索**。企业流程场景用渐进式决策更稳。判断标准：看你的请求主要是结构化还是非结构化。
8. **显式图编排和渐进式决策不冲突**。前者管流程内部流转，后者管入口判断。分层使用确定性手段和 LLM，是最高效的组合。

最后说一句得罪人的话：业界那批"全 LLM 图"框架，demo 很炫，但真到了企业生产，十个有九个会被稳定性、成本、可调试性这三件事劝退，最后要么退化成显式图，要么演化出某种"确定性优先 + LLM 兜底"的渐进式形态。与其走弯路，不如一开始就想清楚——**LLM 是兜底的，不是默认的**。
