# 全书源码之旅的总复盘：如果每个模块只记住一件事

> 这是《WinMatrix 开发经验文集》第 40 篇，也是整个系列的最后一篇。前面 39 篇，有的讲怎么做（01-08 的平台工程），有的讲为什么这么做（10 的反思），有的讲一个模块的深挖（11-22），有的讲跨模块的横切主题（23-30），有的讲和行业的对比（31-35），有的讲踩过的坑（09、36-39）。这一篇不新增内容，而是把散落在 39 篇里的精华，浓缩成一句话。

写到这里，《深入理解 WinMatrix 源码》的 29 章 + 附录我们都过了一遍，配套的文集也到了第 40 篇。这一篇不讲新东西，做一件事：**回头看，每个模块，如果只能记住一件事，该记住什么。**

## ① 基础设施层（ch04-06）

**如果只记住一件事：横切关注点要收口，别靠"大家记得写 try/catch"。**

基础设施层是整个系统最"无聊"也最致命的一层。它不直接产生业务价值，但任何一个基础设施的 bug 都能把整个系统按在地上。

| 模块 | 一句话精华 |
|---|---|
| **数据库与持久化** | single-flight 重建 + 只读重放白名单 + 强制 TimeZone=UTC。连接恢复是并发热点，惊群必须收口。 |
| **缓存与队列** | 配置热更新走 PG LISTEN/NOTIFY 不走 Redis Pub/Sub，且必须直连 PG 不能经 PgBouncer。 |
| **认证与授权** | 双轨权限（静态矩阵编译期 + 动态 RBAC 运行期）+ MCP 多 token 体系（PAT/WMA/WMEC），Token Broker 按前缀路由。 |

这三块的共性是：**它们都是"如果不主动设计，就会散落到几十个文件里的横切逻辑"。** Prisma 的连接恢复、配置变更的传播、token 的鉴权——靠"每个调用方自己处理"是一定会出事的。我们在第 9 篇踩坑文里讲过：横切关注点要用 Proxy / 中间件 / 装饰器收口，封装的标准是"调用方能否假装它不存在"。基础设施层的全部价值，就在于让上层代码忘记它的存在。

一个具体的数字：Prisma 的 single-flight 重建，让整点连接回收时的瞬时连接风暴从"几十个并发请求各自重建"变成了"第一个请求重建、其余等待同一个 Promise"。一个 `if (globalForPrisma.prismaRebuildInFlight)` 守住了整个连接层。

## ② Agent 核心（ch09-12）

**如果只记住一件事：确定性优先于 LLM，LLM 是兜底，不是默认。**

Agent 核心是整个平台最炫的部分——决策引擎、Turn 编排、记忆系统、工具调用循环。但跑过一年多之后，我们最深的体会恰恰相反：**越是核心的决策，越要用便宜的确定性手段兜住大部分情况，把 LLM 留给真正模糊的尾部。**

| 模块 | 一句话精华 |
|---|---|
| **数字员工模型** | 角色（Role）是一等公民。先有角色再有 Agent，DigitalEmployee 是执行编排层、BaseRole 是能力定义层、RoleContext 是运行时数据容器——三层分离。 |
| **渐进式决策引擎** | 5 阶段管线（ExactRouter→Fusion→QuickAccept→Planner→Commitment），80% 的请求在前两阶段就解决了，到不了昂贵的 LLM 规划。 |
| **Turn 执行引擎** | 单轨编排（single-track）+ 三路并行 IO（Promise.all 合并 RTT）+ Tool 循环双终止（iteration + hardCapLlmRounds + roundBudget）。 |
| **记忆系统** | 三层（会话/转录/长期索引）+ 三区检索（Zone1 当前会话、Zone2 项目记忆、Zone3 跨会话降级）。记忆的难题不是检索，是遗忘和噪声控制。 |

这里最值得展开的是决策引擎。一个用户消息进来，怎么决定让哪个员工、用哪个技能、走什么流程？最直觉的答案是"丢给 LLM 规划"。我们一开始也这么想过。但它贵、不稳、且没必要——80% 的请求是模式化的（"生成日会"就该走日会技能）。所以我们做了渐进式管线：**最便宜的阶段先试（精确路由、融合路由），命中就直接返回；不确定的才升级到 LLM。** LLM 的不稳定性被限制在一个可控的尾部。

这个思路推而广之就是技能的 L1/L2/L3 readiness 检查（尽早失败）：L1 决策阶段过滤掉不可用的技能，L2 组装阶段软校验，L3 运行时硬拦。每一层都比下一层便宜，越早过滤掉注定失败的路径，整体越省。**"用 LLM 做决策"的地方，先问一句：这件事能不能用更便宜的确定性手段先过滤掉大部分？** 能，就分阶段。

记忆系统也是一样。我们一度以为"记忆越多越聪明"，后来发现是"记忆越准越聪明"。三区检索里 Zone3（跨会话记忆）的门槛最高（minScore=0.8），而且只有在前两区不足 2 条时才触发——因为跨会话的关联最容易引入噪声。记忆的真正难题不是"怎么记住"，是"怎么不让无关记忆稀释上下文"。

## ③ 技能与工具（ch13-17）

**如果只记住一件事：抽象要带契约，复用和组合才有意义。**

技能和工具是 Agent 的"手"。但企业场景下，"能用"远远不够，还要"可治理、可组合、可审计"。这靠的不是代码写得巧，而是抽象层有没有契约。

| 模块 | 一句话精华 |
|---|---|
| **技能架构** | 技能 = 提示词模板 + Agent 封装 + 契约（provides/consumes）。bundled skill 已 deprecate，artifact-store（产物 + 哈希校验）才是动态能力该有的形态。 |
| **工具执行系统** | 27 个工具域模块，统一 ToolExecutionContext 替代参数注入。声明式操作授权（declaredOperations）——未声明不得从描述推断。 |
| **编码工作站** | 三层镜像（base→engine→component）正交解耦，引擎与运行时分离。所有工作站走远程 sandbox-api（K8s Pod），非本地 docker。 |
| **知识库 RAG** | 全 ES 混合检索（kNN 向量 + BM25），RRF 默认融合。三型一表（document/faq/tfs_git）避免模型爆炸。parent-child 双模式分块复用同一核心算法。 |

技能架构的灵魂是契约。一个技能不只是"一段 prompt"，它声明 `provides: [prd_document]` 和 `consumes: [requirement]`，系统就知道：技术方案这一步要等 PRD 产出，PRD 的产出自动注入技术方案的输入。不需要人写胶水代码。这让技能像积木一样可拼装，多步工作流的串联变成了数据流问题。

这个教训是用代价换来的。早期我们把技能做成了 bundled 的硬编码包，后来发现技能要演进、要热更新、要从市场安装，bundled 路径走不通，最终重构为 artifact-store 模式。**如果你的"能力"需要动态加载、版本管理、热更新，从一开始就用"产物 + 存储 + 哈希校验"的思路，别走硬编码 bundled。**

工具系统则是另一个维度的契约：声明式操作授权。一个工具声明它能做哪些操作（declaredOperations），权限检查就只认声明——未声明的操作，不得从工具描述或关键词推断。这是防 prompt 注入的关键：**LLM 说什么都不算数，只有工具自己声明的才算数。**

编码工作站的三层镜像，是"解耦"的教科书。base image（OCI 基础）、engine image（claude_code/codex/hermes/openclaw 引擎）、component（安装脚本）三个维度正交——你可以换引擎不换运行时，换运行时不换引擎。如果这三层揉在一起，每出一个新引擎就要重新构建所有组合，维护成本爆炸。

## ④ 协作与编排（ch18-22）

**如果只记住一件事：多 Agent 比单 Agent 难一个数量级，别低估它。**

如果你只做单 Agent，恭喜你省了一大半的复杂度。WinMatrix 做的是多数字员工协作，这块的投入远超预期。

| 模块 | 一句话精华 |
|---|---|
| **项目与 PMDOC** | 项目是协作的物理容器（pmdocPath + teamtaskPath 双路径），`00_共享/` 是长期记忆专目录。 |
| **协作会话** | 会话三层分工（conversation_histories 读模型 / session_transcript LLM 真源 / conversation_meta 权威元数据）+ role_inbox 持久收件箱（租约 + 幂等 + turn_id 关联）。 |
| **流程编排** | 三层模型（template 草稿 → template_version 不可变发布版 → run 实例）+ 指令驱动按需编排（每条 instruction 独立 flow_run + claim_token 租约控并发）。 |
| **企业微信接入** | 双轨（长连接 AiBot + Webhook），AiBot WsFrame 转统一消息复用 processMessage 管线。API docid vs 浏览器 pad_id 必须区分。 |
| **MCP 与外部 Agent** | 外部 Agent = 虚拟数字员工（ext_ 前缀防冲突）。分布式 Owner 路由（本地直连 vs 跨实例 RPC），不可达抛 503。 |

协作的复杂度来自"多个自治实体之间的协调"。role_inbox 是这里的精华：它是一个**持久化的、带租约抢占和幂等的收件箱**。一个角色给另一个角色派活，不是直接调函数（函数调用是同步的、脆弱的），而是往收件箱里塞一条消息，由对方的 worker 用租约抢占来认领。失败了重试（retry_count/max_retries），重复了幂等（idempotency_key），轮次关联（turn_id）。这让协作变成了"可靠消息传递"问题，而不是"分布式函数调用"问题。

流程编排的 provides/consumes 契约和技能是一样的思路，但粒度更大——整个流程的步骤之间通过显式契约串联。FlowSkillContractValidationService 强校验：缺失就报 `missing_skill_provides` / `missing_skill_consumes`。**组合的前提是契约，没有契约的组合是赌博。**

## ⑤ 后台与集成（ch23-29）

**如果只记住一件事：状态终态收敛是命门，正常路径走不完时要有代偿。**

后台系统是"看不见但决定生死"的部分。它的核心职责不是"执行任务"，而是"保证任务状态最终收敛"。

| 模块 | 一句话精华 |
|---|---|
| **Worker 系统** | 三进程分离（api/scheduled/rag）+ 进程角色守卫（assertProcessRole）+ 18 个 BullMQ Worker + 4 个补偿 Scanner。 |
| **定时任务** | 16 个系统任务，三队列按重量分流（scheduled-agent 重 / scheduled-system 维护 / scheduled-light 轻扫）。09:00 尖峰 cron 用迁移审计表做存量迁移。 |
| **可观测性** | ExecutionSpan 是 retire-agent-execution-log 后的 SSOT。三 Sink 路由（UnifiedObservabilityRule 决定落 span/log/channel）。LLM 调用强制 I/O 可读（start 必含 request，end 必含 response）。 |
| **构建部署** | 四进程对齐（dev 四终端 ↔ prod 四服务 ↔ k8s 主应用+worker 分离）。esbuild 主构建 + tsc 校类型。Makefile 覆盖全镜像矩阵。 |
| **测试策略** | E2E 坚决不 mock 数据库（缺失必填项直接 exit(1)）。真实事故回放 fixture（incident-2026-05-26）。四 project 分级 timeout。 |
| **设计哲学** | 六层分层 + import 门禁（check:layers 存量 allowlist + check:agent-layers:strict 增量零容忍）。时间统一真源 = Pod TZ（禁 toISOString 流出、禁硬编码时区）。Port 注入 17+ 业务 Port。 |

这一块最核心的洞见，来自踩坑系列（36-39）：**任何"running 状态"都必须有收敛到终态的保障机制。** 进程会崩、网络会断、外部调用会悬挂——正常路径总有走不完的时候。一个可靠的系统，不在于正常路径多完美，而在于正常路径走不完时，有没有代偿机制来收尾。

- 悬挂的 LLM 调用 → `llmCallWatchdogSweeper` 每 10 分钟扫描代偿补写 end
- 进程崩溃留下的 running 任务 → 启动时 `reconcileStaleRunsOnBootstrap` 用 advisory lock 串行收敛
- Schema 漂移 → 启动 information_schema 探测 + 运行期 P2021/P2022 识别 + HTTP 503 降级
- WebSocket 半断开 → 协议层 ping/pong + 重连 `connection:sync` 先注册后读取

这四个机制，本质都是同一个信念：**正常路径负责"把事情做对"，代偿机制负责"当正常路径走不完时，把事情收尾"。两者缺一不可。** 只有正常路径的系统，顺境完美、逆境崩溃。加上代偿，系统才有韧性。

可观测性是另一根命门。我们在第 8 篇讲过：ExecutionSpan 取代了散落的 `agent_execution_log`，成为单一事实来源（SSOT）。一次对话里"谁、什么时候、做了什么、成功没"，一句 SQL 就出来了。**在写第一个 Agent 之前就把 span 追踪搭好**——等到生产事故来了再补，面对的是几百万行无法关联的日志。

## ⑥ 工程实践与哲学

**如果只记住一件事：模型是引擎，工程是底盘。引擎再猛，底盘散架，车还是开不到终点。**

做 AI 平台这一年多，最深的感受是：**模型在飞速进步，但工程问题几乎没变。**

新的模型让"能做什么"的天花板不断抬高，但真正决定一个产品能不能在企业里活下来的，还是那些老掉牙的工程基本功：

- **分层**。5 大层 + Agent 内部 6 子层，import 门禁双门（存量 allowlist + 增量零容忍）。没有分层的系统，迭代几次就糊成一团。
- **契约**。技能的 provides/consumes、工具的 declaredOperations、流程的 inputSchema/outputSchema——凡是想复用和组合的，都要有明确的输入输出契约。
- **可观测性**。span 树是 Agent 时代的"日志"，第一天就搭好。LLM 调用强制 I/O 可读（request/response 必含）。
- **错误恢复与终态收敛**。single-flight、悬挂看门狗、启动对账、半断开检测——正常路径走不完时的代偿。
- **文档治理**。架构 SSOT 在一处（AGENTS.md），其他都是链接。散落的文档比没有文档更危险，因为它制造"我知道"的幻觉。
- **向后兼容的策略**。功能重构默认不需要向后兼容，除非明确说明。包袱轻了，迭代快了。

这些里没有一条是"AI 特有的"。它们是过去几十年软件工程沉淀下来的基本功，套了一层 AI 的皮。但正因为它们不新鲜，反而最容易被忽视——大家的注意力都在 prompt、模型、agent 上，没人愿意花时间在"连接池怎么恢复""状态怎么收敛""日志怎么关联"上。

**但决定生死的，恰恰是后者。**

## 给后来者的八句话

把 40 篇的精华，再压一层。如果你只读这一段，记住这八句：

1. **定位决定架构。** "AI 是工具"和"AI 是员工"是两个完全不同的产品，别用同一个架构硬套。
2. **确定性优先于 LLM。** 能用规则、路由、模式匹配解决的，别上 LLM。LLM 是兜底，不是默认。
3. **尽早失败，分层检查。** L1/L2/L3 的思路适用于一切"要不要执行"的判断。
4. **抽象要带契约。** 技能、工具、流程，凡是想复用和组合的，都要有明确的输入输出契约。
5. **可观测性先行。** span 树是 Agent 时代的日志，第一天就搭好。等事故来了再补，来不及。
6. **横切关注点收口。** 连接恢复、鉴权、限流、追踪——用 Proxy/中间件统一处理，别靠纪律。
7. **正常路径配代偿机制。** 外部调用必有悬挂检测，持久 running 必有启动对账，长连接必有半断开探测。
8. **动态能力用产物模式。** 需要热更新、版本、市场分发的东西，别硬编码 bundled。

## 写在最后

写这 40 篇的过程，也是我们重新审视整个代码库的过程。好几处"我以为是这样，写出来发现其实是那样"的地方，都在这个过程中被纠正了。文档治理和代码治理一样重要——**写不出清晰文档的系统，多半是没想清楚的系统。**

我们也走过弯路。早期对"向后兼容"太执着，系统里长期挂着两套并行实现；文档一度散落在四五处，彼此可能滞后；数字口径（几个模型、几个技能、几层记忆）在不同时期的文档里对不上。这些都是真问题，不是吹毛求疵。但每一次发现，都是一次收敛——这本书的写作过程本身，就是一次大规模的 SSOT 治理。

做 AI 平台这件事，最迷人的地方在于：它要求你同时是最乐观的（相信 AI 能做到）和最悲观的（假设一切都会出错）的工程师。乐观让你敢想，悲观让你把底盘做扎实。这 40 篇里，前一半的底气来自乐观，后一半的韧性来自悲观。两者缺一不可。

模型是引擎，工程是底盘和转向。引擎再猛，底盘散架，车还是开不到终点。

希望这 40 篇，能帮你在"AI 员工"这条路上，把底盘做扎实一点。
