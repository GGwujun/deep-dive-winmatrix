# 重放 ≠ 永远安全：哪些操作能自动重试

> 这是《WinMatrix 开发经验文集》第 57 篇。上一篇讲横切收口，提到 Prisma Proxy 会"自动重放只读方法"。这一篇就专门拆这个"只读"——为什么是只读？写操作为什么不能重放？自动重试听起来是好事，为什么不能无脑开？这一篇的核心论点有点反直觉：**重放和重试是两回事，重试有时候会把一个"瞬时错误"悄悄换成一个"数据错误"，而后者是不可逆的。** 判断哪些操作能自动重试，是分布式系统设计里最容易拍脑袋、也最容易出事的一个决定。

先讲一个把人坑惨了的"好心办坏事"。

某个服务调用 DB 写一条记录，遇到了网络超时。服务想："超时嘛，重试一次就好了。" 于是它重试了。但真相是——第一次调用其实成功了，只是响应包在路上丢了。重试导致同一条记录被写了两次，唯一约束冲突，第二次抛错。这个错误看起来是"重试失败"，没什么大不了的。

但换个场景就可怕了。某个服务调用的是"扣余额"，遇到了超时。它重试了。第一次其实扣了 100 块，重试又扣了 100 块。用户余额直接扣了 200。**这就是重试把"瞬时错误"（网络超时）换成了"数据错误"（重复扣款）——前者重试就好，后者不可逆。**

这个例子的教训是：**重试是否安全，不取决于错误类型，而取决于被重试的操作本身的性质。** 只读操作怎么重试都安全（它不改状态），写操作重试前必须确认它的幂等性。这一篇讲 WinMatrix 在两个层面怎么落地这个判断——Prisma 重建后的重放白名单，和 BullMQ 的延迟重投。

---

## 第一层：Prisma 重建后的只读重放白名单

上一篇讲过，Prisma Proxy 遇到可恢复错误会 single-flight 重建连接池，然后**对只读方法自动重放一次**。现在要回答的关键问题是：**怎么判断"只读"？**

WinMatrix 用的是一个**显式白名单**（`shouldReplayAfterPrismaRebuild`，`client.ts:289-301`，核实报告 ch04-06）：

```
可重放的白名单（11 种只读方法）：
  findMany / findFirst / findFirstOrThrow
  findUnique / findUniqueOrThrow
  aggregate / count / groupBy
  $queryRaw / $queryRawUnsafe
  $connect

不可重放（写方法，一律排除）：
  create / createMany / update / updateMany / upsert / delete / deleteMany
  $executeRaw / $executeRawUnsafe    ← 注意：raw 执行方法不在白名单，哪怕是 SELECT 语义也不重放
  $transaction
```

注意一个容易想当然的细节：**`$executeRaw` / `$executeRawUnsafe` 不在白名单里**，哪怕你写的是一条 `SELECT`。原因是框架无法静态判断一段 raw SQL 的语义（它可能是 `SELECT ... FOR UPDATE`、带副作用 CTE、甚至 `INSERT ... RETURNING`），只能一刀切排除。如果你有"只读 raw SQL"想要重放，得走 `$queryRaw` 这条被白名单认可的路径。这正是白名单"保守优先"的体现。

为什么用显式白名单而不是"分析 SQL 判断是不是 SELECT"？这是个看似可以自动化、实则不能的设计。原因是：

**第一，白名单是保守的，自动化是激进的。** 白名单只重放确认安全的 11 种方法，其他一律不重放（即使某些写操作理论上幂等）。这是 fail-closed——宁可少重放，绝不错重放。自动化判断 SQL 会遇到各种边界（带 RETURNING 的 INSERT、CTE 里的 UPDATE、触发器副作用），一旦判断错，就是数据错误。

**第二，写操作的幂等性是业务决定的，不是框架能判断的。** `updateMany({ where: { status: 'pending' }, data: { status: 'done' } })` 这个操作幂等吗？取决于业务——如果"done"是终态，重试无害；如果"done"会触发副作用（比如发通知），重试就是重复通知。框架没法知道，只有业务知道。所以框架的选择是：**写操作一律不自动重放，让业务层自己决定。**

重放决策的完整逻辑（`withPrismaRecovery`，`client.ts:305-332`）：

```
请求 → Prisma 调用 → 连接池错误
                      │
                      ├── isRecoverablePrismaPoolError(err)？
                      │     ├── 否 → 抛错（业务错误如唯一约束，不重建）
                      │     └── 是 → single-flight 重建
                      │              │
                      │              ├── shouldReplayAfterPrismaRebuild(method)？
                      │              │     ├── 是（只读白名单）→ 重放一次
                      │              │     │     ├── 成功 → 返回结果（用户无感）
                      │              │     │     └── 失败 → 抛错
                      │              │     └── 否（写方法）→ 抛错（让业务层处理）
                      │              │
                      │              └── 重建失败 → 抛错
```

注意三个关键决策点：

- **不是所有错误都重建**——`isRecoverablePrismaPoolError` 识别 9 种可恢复模式（连接超时、连接断开等），业务错误（唯一约束冲突等）不重建。因为业务错误重试也没用。
- **重建后不是所有方法都重放**——只读白名单重放，写方法直接抛错。
- **重放只重试一次**——不无限重试。一次重放失败就抛错，避免重试风暴。

**这套逻辑的精髓是：把"可恢复错误"和"可重放操作"分成两个独立的判断。** 一个操作能不能被自动恢复，等于"错误是瞬时的" AND "操作是只读的"。两个条件缺一个，都不自动重试。

## 第二层：BullMQ 的 DelayedError——重投而不是重试

第二个层面是消息队列。BullMQ 的语义是 at-least-once（至少一次），这意味着消息可能被重复投递。WinMatrix 在"超并发"场景下用了一个更精细的机制——`moveToDelayed + DelayedError`（核实报告 ch23-29）：

```
crossAgentTriggerWorker 与 scheduled-agent 共享 getScheduledAgentSemFromEnv
（全局信号量，控制 LLM 并发）
  │
  ▼ 拿不到信号量（并发已满）
  │
  moveToDelayed + throw DelayedError
  │  → 任务被移到延迟队列，稍后重投
  │  → 不是失败，不是丢弃，是"延迟重投"
```

这里的关键区分是：**"重试"和"重投"是两回事。**

- **重试（retry）**：同一个 worker 立刻再处理一次。适用于"瞬时错误"（网络抖动、连接超时）。
- **重投（requeue/delayed）**：把任务放回队列，等一段时间后可能被另一个 worker 处理。适用于"资源不足"（并发已满、依赖未就绪）。

拿不到信号量这个场景，用重试是错的——你立刻再试一次，信号量还是满的（其他任务还占着），只会陷入 busy-loop。正确做法是 `moveToDelayed`：把任务往后挪，让当前占着信号量的任务先跑完，过一会儿再重投。这是"把任务排到队尾"，不是"重试"。

**BullMQ 的 `attempts: 2`（指数退避 5s）是真正的重试**（核实报告 ch23-29，queue.ts:17-28），用于处理真正的瞬时失败（worker 跑到一半崩了）。而 `DelayedError` 是"主动延迟"，用于资源调度。两者配合：

```
任务执行
  ├── 资源不足（信号量满）→ moveToDelayed + DelayedError → 延迟重投
  ├── 瞬时错误（崩溃/超时）→ BullMQ 自动 retry（attempts:2，5s 退避）
  └── 业务失败 → 记录失败，不重试
```

**这套逻辑的精髓是：区分"为什么要重做"，按原因选择不同的"重做"机制。** 资源不足用延迟重投，瞬时错误用有限重试，业务失败不重做。

## 把两层抽象成一个判断矩阵

把 Prisma 重放和 BullMQ 重投抽象成一张矩阵，"能不能自动重试"的判断标准就清晰了：

| 错误类型 | 操作类型 | 正确做法 | WinMatrix 例子 |
|---------|---------|---------|---------------|
| 瞬时错误（连接池/网络） | 只读 | 自动重放一次 | Prisma Proxy 重放白名单 |
| 瞬时错误（连接池/网络） | 写 | 不重放，抛错给业务层 | Prisma Proxy 拒绝重放写方法 |
| 瞬时错误（崩溃/超时） | 队列任务 | 有限重试（attempts:2） | BullMQ defaultJobOptions |
| 资源不足（并发满） | 队列任务 | 延迟重投（不占重试次数） | moveToDelayed + DelayedError |
| 业务错误（唯一约束等） | 任意 | 不重试，直接失败 | isRecoverablePrismaPoolError 排除 |
| 业务失败（逻辑错） | 任意 | 不重试，记录失败 | 任务失败状态 |

这张矩阵的核心规律是：**重试的安全性 = 错误瞬时性 × 操作幂等性。**

- 错误是瞬时的 AND 操作是幂等的 → 可以自动重试。
- 错误是瞬时的 BUT 操作不幂等 → 不能自动重试（可能重复执行）。
- 错误不是瞬时的（业务错） → 无论操作幂不幂等，重试都没用。

**"只读"是"幂等"的最强形式**——只读操作对状态零影响，重试一万次也安全。所以 Prisma 重放白名单只放只读方法，这是最保守、最安全的策略。写操作的幂等性需要业务层自己保证（参考第 23 篇幂等设计的 5 种形态），框架不能越俎代庖。

## 为什么"默认重试"是危险的

很多框架的默认行为是"遇到错误自动重试 N 次"。听起来很贴心，但这个默认值是危险的。原因有三个。

**第一，重试会放大流量。** 1000 个请求遇到瞬时错误，每个重试 3 次，瞬间变成 4000 个请求打到下游。如果下游本来就是压力过大才报错，重试会让它彻底崩。这就是"重试风暴"。WinMatrix 的 Prisma 重放**只重试一次**，而且写操作不重试，就是为了控制放大倍数。BullMQ 的 retry 也只有 `attempts: 2`。

**第二，重试会把瞬时错误换成数据错误。** 开头讲的"扣余额重试扣两次"就是典型。一旦换成数据错误，问题从"可恢复的瞬时故障"变成"不可逆的数据损坏"。**这是重试最阴险的危害——它看起来是在解决问题，实际上是在制造更严重的问题，而且很安静。**

**第三，重试会掩盖根因。** 如果某个操作频繁失败被自动重试救回，表面的"成功率"是虚高的。没人会去查根因，直到某天重试也救不回来，才发现问题早就存在。WinMatrix 的做法是：重建后打 warn 日志（`logger.warn('[Prisma] 检测到可恢复连接池错误，已重建...')`），让运维能看到重建频率——频繁重建说明有更深层的问题，不能靠重试掩盖。

---

## 判断"能不能自动重试"的三步法

把 WinMatrix 的实践提炼成一个可操作的三步判断法：

**第一步：错误是瞬时的还是永久的？**
- 瞬时（连接断、超时、网络抖动）→ 进入第二步。
- 永久（唯一约束、权限不足、参数错误）→ 不重试，立刻失败。
- WinMatrix 用 `isRecoverablePrismaPoolError` 识别 9 种瞬时模式，其他一律当永久错误。

**第二步：操作是只读/幂等的，还是写的/不幂等的？**
- 只读或确认幂等 → 可以自动重试。
- 写且不幂等 → 不能自动重试，让业务层处理。
- WinMatrix 用 `shouldReplayAfterPrismaRebuild` 白名单（11 种只读方法，`$executeRaw` 即使是 SELECT 也不在内），写方法一律不重放。

**第三步：重试的"成本"可控吗？**
- 重试次数有限（1-2 次）→ 可以。
- 重试会无限循环或放大流量 → 改用延迟重投（moveToDelayed），或直接失败。
- WinMatrix：Prisma 重放只 1 次，BullMQ retry 只 2 次，资源不足用 DelayedError 延迟重投。

**任何一步过不了，都不自动重试。** 这个三步法是保守的，但重试这个领域，保守是对的——每多一次自动重试，就多一次把瞬时错误换成数据错误的机会。

## 给后来者的总结

1. **重试是否安全，不取决于错误类型，而取决于操作性质。** 错误瞬时性 × 操作幂等性 = 重试安全性。两个都满足才能自动重试。
2. **只读操作是幂等的最强形式，怎么重试都安全。** Prisma 重放白名单只放 11 种只读方法（findMany/findFirst/findUnique/aggregate/count/groupBy/$queryRaw 等，`$executeRaw` 即使 SELECT 语义也不放），这是最保守也最安全的策略。
3. **写操作不要自动重试。** 写操作的幂等性是业务决定的（参考第 23 篇 5 种幂等形态），框架不能越俎代庖。Prisma Proxy 对写方法一律抛错，让业务层自己决定。
4. **用显式白名单，不要自动分析 SQL 判断只读。** 白名单保守但安全（fail-closed），自动判断激进且会踩到各种边界（RETURNING、CTE、触发器）。
5. **区分"重试"和"重投"。** 瞬时错误用有限重试（BullMQ attempts:2），资源不足用延迟重投（moveToDelayed + DelayedError）。两者配合，不要混用。
6. **重试次数要有限，防止重试风暴。** Prisma 重放只 1 次，BullMQ retry 只 2 次。无限重试会放大流量，把下游打崩。
7. **重试最大的危害是把瞬时错误换成数据错误。** 而且这个过程很安静——代码看起来成功了，数据却错了。这种 bug 极难发现。
8. **重试不要掩盖根因。** 重建/重试要打日志，让运维能看到频率。频繁重建说明有更深的问题，不能靠重试粉饰成功率。

重试是这个行业最容易被滥用的机制。每个框架都提供"自动重试"，默认值看起来很贴心，但它背后藏着的"瞬时错误→数据错误"的转换，是无数生产事故的根源。**判断一个系统成熟的标志之一，是看它对"自动重试"有多克制。** 每多一份克制，就少一个深夜被叫醒的数据修复事故。这不是技术问题，是工程伦理。
