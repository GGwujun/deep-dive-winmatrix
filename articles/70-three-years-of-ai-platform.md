# 全系列终章：做 AI 平台三年，我会告诉刚开始的自己什么

> 这是《WinMatrix 开发经验文集》第 70 篇，也是整个 01-70 文集的正式完结。前面 69 篇，有的讲怎么做（核心引擎、技能、协作），有的讲为什么这么做（反思、设计哲学），有的讲怎么踩的坑（基础设施、启动序列、prompt 漂移）。这一篇不新增内容，而是跳出 WinMatrix，把 69 篇里最普适的教训浓缩成给"刚开始做 AI 平台的人"的忠告。

写到这里，这套文集到了第 70 篇。

70 篇是个不小的数字。第一批 10 篇（01-10）讲核心机制：Turn 引擎、决策、记忆、流式、工具、技能、协作、可观测，踩坑和反思收尾。第二批 30 篇（11-40）是源码深挖 + 横切主题 + 行业对比 + 踩坑扩展 + 总复盘。第三批 30 篇（41-70）往更细的源码、更深的工程哲学、更多的延伸踩坑方向挖，直到这一篇。

这三批 70 篇，覆盖了 WinMatrix 这个企业级 AI 数字员工协作平台从数据库到 prompt、从启动序列到优雅停机、从单 Agent 决策到多 Agent 协作的几乎所有工程维度。配套的还有《深入理解 WinMatrix 源码》全书 29 章 + 附录、157 张数据库表、几十万行 TypeScript。

但这一篇不想再讲 WinMatrix 的任何一个具体模块。这一篇想回答一个更宏大的问题：**如果我能穿越回三年前，站在这条路的起点，我会告诉当时的自己什么？**

下面分五块——产品定位、架构、Agent 核心、工程基本功、团队——每块几条最普适的教训。它们不是 WinMatrix 特有的，是任何"做 AI 平台"的人迟早会撞上的。

## 一、关于产品定位：先想清楚"AI 是什么"

**第一句话，也是最重要的一句话：定位决定架构，而架构决定你后面三年的痛苦来源。**

"AI 是工具"和"AI 是员工"是两个截然不同的产品。工具型 AI（ChatGPT、Copilot）的架构核心是"一个大脑 + 一堆工具"——用户驱动，AI 辅助。员工型 AI（WinMatrix 这类）的核心是"先有角色，再有 Agent"——AI 自主，人类监督。

这两个方向的产品，架构几乎不通用。如果你用工具型架构去做员工型产品，会发现 AI 没有持续身份、没有协作语义、没有责任边界；反过来也一样。我们在第 10 篇和第 31 篇详细对比过这两种思路。

**第二句话：toB 和 toC 的 AI 产品，难的地方完全不同。** toC 难在"智能的天花板"——模型够不够强、回答够不够惊艳。toB 难在"工程的地板"——能不能稳定地、可审计地、可治理地跑在企业里。前者吸引眼球，后者决定生死。如果你做 toB，请把大部分精力放在后者：分层、契约、可观测性、权限、审计、降级、终态收敛。这些听起来不性感，但它们是企业敢不敢用你的前提。

**第三句话：别低估"多 Agent 协作"的复杂度。** 如果只做单 Agent，你省了至少一半的工程复杂度。多 Agent 的协作——谁主导、谁配合、消息怎么派发、结果怎么汇总、冲突怎么解决——比单 Agent 难一个数量级。WinMatrix 为此做了 role_inbox（持久收件箱 + 租约 + 幂等）、流程编排（三层模板 + 指令驱动）、协作催促（延时任务 + 全生命周期）一整套。如果你不确定自己真的需要多 Agent，先从单 Agent 做起。

**第四句话：配置即数据。** agent_config、skill_artifact、route_rule、prompt_section、tool_config——凡是会变的、需要热更新的、需要审计的、需要版本管理的，都放数据库，不要放配置文件或代码。我们在第 58 篇讲过这个哲学：配置入库意味着热更新（改 DB 即时生效）、审计（谁改了什么）、版本（可回滚）、治理（权限可管控）。代价是配置漂移，要用三层防御（启动检测、运行期识别、HTTP 503 降级）兜住。

## 二、关于架构：分层、契约、解耦

**第一句话：分层不是画图，是执行。** 一张漂亮的架构图谁都会画，但它能不能在几十万行代码、十几个人、两三年迭代后还成立，取决于你有没有给它配上"自动守卫"。WinMatrix 的分层能守住，靠的是两个门禁脚本：`check:layers`（大层门禁，存量白名单 + 增量零容忍）和 `check:agent-layers:strict`（Agent 子层门禁，R1-R7 零容忍）。没有这两个脚本，我们的五层架构早就糊成一团了。第 66 篇详细讲了这套门禁的设计。

**第二句话：抽象要带契约。** 技能的 provides/consumes、工具的 declaredOperations、流程的 inputSchema/outputSchema——凡是想复用和组合的，都要有明确的输入输出契约。没有契约的组合是赌博：你以为这个技能产出的是 PRD，它却产出了半成品，下游技能拿不到预期输入就崩了。WinMatrix 的 FlowSkillContractValidationService 强校验契约，缺失就报 `missing_skill_provides`。第 6、7、20 篇都讲过这个。

**第三句话：横切关注点别靠纪律，要用 Proxy/中间件/Hook 收口。** 连接恢复、鉴权、限流、追踪、prompt 拼装——这些逻辑如果散落到几十个调用方里，一定会有人写错。我们在 Prisma 客户端包了一层带 single-flight 重建 + 重放白名单的 Proxy（第 9 篇），让业务代码"假装连接恢复不存在"。封装的标准是：调用方能否假装它不存在。如果业务代码里出现了"重建连接池"的字样，封装就失败了。第 56 篇专门讲了这个哲学。

**第四句话：横向隔离比纵向分层更难、更值钱。** 纵向分层（不能反向依赖）大家容易想到。但横向隔离——L3 harness 与 L4 domain-harness 不互相 import、channel 与 connectors 不互相耦合——往往被忽略，而它恰恰是"能不能独立演进、独立复用"的关键。WinMatrix 的 R4 和 R6 门禁专门盯横向隔离（第 66 篇）。如果两个本该独立的包焊死了，任何一边的改动都会牵动另一边，迭代就会越来越慢。

**第五句话：Port 注入解耦，但启动期要 fail-fast。** Agent 不直 import Business，而是通过 17+ 个业务 Port 在启动时注入。这让 Agent 和 Business 可以独立编译、独立演进。但代价是启动序列变得脆弱——顺序错了、Port 注入了 undefined，运行时会崩。解决办法是塞满断言：assertCoreDiRegistrations、assertAgentBusinessPortsWired、adapter 数量必须等于 4。启动期能查出来的问题，绝不让它活到运行时（第 67 篇）。

## 三、关于 Agent 核心：确定性优先，LLM 是兜底

**第一句话：确定性优先于 LLM。这是整个 Agent 设计里最重要的一句话。** 能用规则、路由、模式匹配解决的，别上 LLM。LLM 是兜底，不是默认。WinMatrix 的渐进式决策引擎分 5 个阶段：精确路由 → 融合路由 → 快速接受 → LLM 规划 → 承诺派生。80% 的请求在前两个阶段就解决了，根本到不了昂贵的 LLM 规划。这个设计让成本和延迟都下来了，也让 LLM 的不稳定性被限制在一个可控的尾部（第 2 篇）。

**第二句话：尽早失败，分层检查。** L1/L2/L3 的思路适用于一切"要不要执行"的判断。L1 最便宜（技能存在吗、启用了吗），L2 中等（依赖的输入满足吗），L3 最贵（运行时资源就绪吗）。越早过滤掉注定失败的执行，整体越省。别让一个注定失败的执行跑到一半才崩——那是算力、token、用户耐心的三重浪费（第 2、6 篇）。

**第三句话：记忆的难题不是"记住"，是"遗忘"和"噪声控制"。** 我们一度以为"记忆越多越聪明"，后来发现是"记忆越准越聪明"。WinMatrix 的三区检索，Zone3（跨会话记忆）门槛最高（minScore=0.8），而且只有前两区不足 2 条时才触发——因为跨会话的关联最容易引入噪声。注入无关记忆不仅不增智，还会稀释上下文、误导模型。记忆治理的核心是"怎么不让无关记忆稀释上下文"（第 3 篇）。

**第四句话：Tool 循环必须有双终止 + 预算。** `iteration < maxIterations` AND `totalLlmRounds < hardCapLlmRounds`——两道上限。再加上 `roundBudgetMs` 超预算终止。没有硬上限的 Tool 循环，模型会陷入"调工具 → 看结果 → 再调工具"的死循环，token 烧光用户也没等到答案。豁免工具（如只读查询）可以不占配额，但写操作必须计入（第 1、5 篇）。

**第五句话：prompt 是配置，不是代码——要版本化、可热更新、可观测。** prompt 改了，正在进行的会话用新还是旧？缓存怎么失效？版本怎么回滚？这些问题比"prompt 怎么写"难十倍。WinMatrix 用 prompt_section + agent_prompt_template 两张表，每槽位单 enabled 不变式（事务守护）、三层缓存（内存 + Redis + registry）、增量热更新（refreshById + 全量兜底）、span 记录 promptId + version + contentHash，把 prompt 治理工程化了（第 69 篇）。prompt 既是代码（决定行为）又是数据（存 DB、会被缓存），兼具两者复杂性，必须按"带版本的运行时配置"对待。

**第六句话：可观测性是 Agent 时代的一等公民。** ExecutionSpan 取代了散落的日志表，成为单一事实来源（SSOT）。一次对话里"谁、什么时候、做了什么、成功没"，一句 SQL 出来。在写第一个 Agent 之前就把 span 追踪搭好——等事故来了再补，面对的是几百万行无法关联的日志。LLM 调用强制 I/O 可读：start 必含 request.messages，end 必含 response（第 8、50 篇）。

## 四、关于工程基本功：模型是引擎，工程是底盘

**第一句话：模型是引擎，工程是底盘和转向。引擎再猛，底盘散架，车还是开不到终点。** 这是整个 70 篇反复出现的主线。新的模型让"能做什么"的天花板不断抬高，但真正决定一个产品能不能在企业里活下来的，还是那些老掉牙的工程基本功——分层、契约、可观测性、错误恢复、文档治理、向后兼容的策略。它们不新鲜，反而最容易被忽视（第 10、40 篇）。

**第二句话：正常路径配代偿机制，状态终态收敛是命门。** 任何"running 状态"都必须有收敛到终态的保障。进程会崩、网络会断、外部调用会悬挂——正常路径总有走不完的时候。一个可靠的系统，不在于正常路径多完美，而在于正常路径走不完时，有没有代偿机制来收尾：

- 悬挂的 LLM 调用 → `llmCallWatchdogSweeper` 每 10 分钟扫描代偿补写 end（第 36 篇）
- 进程崩溃留下的 running 任务 → 启动时 `reconcileStaleRunsOnBootstrap` 用 advisory lock 串行收敛（第 37 篇）
- Schema 漂移 → 启动 information_schema 探测 + 运行期 P2021/P2022 识别 + HTTP 503 降级（第 38 篇）
- WebSocket 半断开 → 协议层 ping/pong + 重连 `connection:sync` 先注册后读取（第 39 篇）

正常路径负责"把事情做对"，代偿机制负责"当正常路径走不完时把事情收尾"。两者缺一不可（第 51 篇）。

**第三句话：可重放性是调试的前提。** 一个 bug 能不能"按原样再跑一遍"，决定了你调试它的效率。WinMatrix 的 span 树 + session_transcript + 事件 seq，让任意一次执行可回放。我们甚至把生产事故的 fixture（incident-2026-05-26）固化下来做回归测试。不可重放的 bug，调试全靠猜；可重放的 bug，改个参数就能复现（第 53 篇）。

**第四句话：优雅降级要分层设计。** 当 Redis、ES、BullMQ、LLM 分别挂掉时，系统怎么活？Redis 挂了走内存降级、ES 挂了走纯 PG BM25、BullMQ 挂了走内存队列、LLM 挂了走规则兜底。每一层都要想清楚"挂了怎么办"，而不是假设它们永远可用。第 25 篇专门讲了这套降级矩阵。

**第五句话：定时任务、cron、队列这些"后台基础设施"不能马虎。** 所有人 cron 都设在整点，整点就是 DB 尖峰——用 hash 打散 + 审计表幂等迁移（第 68 篇）。队列要按重量分流——BullMQ 三档（scheduled-agent 重 / scheduled-system 维护 / scheduled-light 轻扫），不要一个队列塞所有任务（第 17 篇）。超载时 `moveToDelayed + DelayedError` 延迟重投，而不是丢弃（第 62 篇）。这些后台逻辑看不见，但决定系统在压力下的韧性。

**第六句话：文档治理和代码治理一样重要。** 架构 SSOT 在一处（AGENTS.md），其他都是链接。散落的文档比没有文档更危险，因为它制造"我知道"的幻觉。数字口径（几个模型、几个技能、几层记忆）在不同文档里对不上，暴露的是"有没有人真的在维护事实"。这套 70 篇的写作过程本身，就是一次大规模的 SSOT 治理——好几处"我以为是这样，写出来发现其实是那样"的地方被纠正了（第 10、40 篇）。

## 五、关于团队与心态：乐观与悲观缺一不可

**第一句话：做 AI 平台，要同时是最乐观和最悲观的工程师。** 乐观让你敢想——相信 AI 能做到那些看似不可能的事，敢把模型塞进业务流程的核心。悲观让你把底盘做扎实——假设一切都会出错，进程会崩、网络会断、LLM 会悬挂、数据会脏、用户会乱点。前一半的底气来自乐观，后一半的韧性来自悲观。两者缺一不可（第 40 篇）。

**第二句话：向后兼容的策略要想清楚，别无脑保留旧路径。** 早期我们对"向后兼容"太执着，功能重构时总想保留旧路径，结果系统里长期挂着两套并行的实现，维护成本翻倍。后来定了规矩：功能重构默认不需要向后兼容，除非明确说明。包袱轻了，迭代快了。但这不意味着随便破坏——是对"要不要保留旧路径"做有意识的取舍，而不是无脑保留（第 10 篇）。

**第三句话：数字分身、多租户这类"扩展性需求"，要第一天就考虑。** 数字分身（同一个角色的个性化实例）如果是后期硬加的，要么复制一套平行实现（维护噩梦），要么改动会波及所有现有逻辑。WinMatrix 的做法是"同源继承"：新增能力默认对分身生效，排除须显式名单，禁止平行实现。多租户也是——project_id 维度的数据/工具/记忆/队列隔离，如果后期加，迁移成本巨大。第一天就把这些维度想进去，比后期硬塞便宜得多（第 59 篇、事实清单）。

**第四句话：踩坑是常态，关键是要把每个坑变成机制。** 我们踩过的坑——Prisma 时区偏移 8 小时、连接池整点风暴、启动 DI 注册顺序、cron 整点拥挤、prompt 缓存不失效——每一个都是真实事故。但每个坑修完，都沉淀成了一个机制：TimeZone=UTC 强制、single-flight 重建、fail-fast 断言、spread-cron 迁移、三层缓存热更新。踩坑不可怕，可怕的是踩了同一个坑两次。把坑变成机制，就是用工程手段对抗人类的健忘。

**第五句话：模型在飞速进步，但工程问题几乎没变。** 这是最深的一个体会，也是整个 70 篇反复印证的一句话。三年前我们纠结的"LLM 调用怎么不悬挂""状态怎么收敛""prompt 怎么版本化"，今天依然在纠结。新的模型让"能做什么"不断扩展，但"怎么稳定地、可治理地、可观测地做"——这些工程基本功，套一层 AI 的皮，还是过去几十年软件工程沉淀的那些东西。大家注意力都在 prompt、模型、agent 上，没人愿意花时间在连接池、状态机、文档治理上。但决定生死的，恰恰是后者。

## 给刚开始做 AI 平台的你的十句话

把 70 篇的精华，再压一层。如果你只读这一段，记住这十句：

1. **定位决定架构。** "AI 是工具"和"AI 是员工"是两个产品，别用同一个架构硬套。
2. **确定性优先于 LLM。** 能用规则、路由、模式匹配解决的，别上 LLM。LLM 是兜底。
3. **尽早失败，分层检查。** L1/L2/L3 适用于一切"要不要执行"的判断。
4. **抽象要带契约。** 技能、工具、流程，凡是想复用和组合的，都要有明确契约。
5. **可观测性先行。** span 树是 Agent 时代的日志，第一天就搭好，prompt 版本写进 span。
6. **横切关注点收口。** 连接恢复、鉴权、限流、追踪——用 Proxy/中间件统一，别靠纪律。
7. **正常路径配代偿机制。** 外部调用必有悬挂检测，持久 running 必有启动对账，长连接必有半断开探测。
8. **配置即数据 + 版本化 + 单 enabled 不变式。** prompt、技能、路由都是配置，入库、版本化、可回滚、热更新。
9. **分层要靠门禁脚本守住。** 存量白名单 + 增量零容忍；横向隔离比纵向分层更值钱。
10. **模型是引擎，工程是底盘。** 引擎再猛，底盘散架，车开不到终点。把时间花在底盘上。

## 写在最后

写这 70 篇的过程，也是我们重新审视整个代码库、重新梳理三年工程经验的过程。好几处"我以为是这样，写出来发现其实是那样"的地方，都在这个过程中被纠正了。文档治理和代码治理一样重要——**写不出清晰文档的系统，多半是没想清楚的系统。**

我们也走过很多弯路。早期对"向后兼容"太执着，系统里长期挂着两套并行实现；文档一度散落在四五处，彼此可能滞后；数字口径在不同时期的文档里对不上；prompt 改了缓存不失效、cron 全挤在整点、启动序列注册顺序错乱……这些都是真问题，不是吹毛求疵。但每一次发现，都是一次收敛——这 70 篇的写作过程本身，就是一次大规模的 SSOT 治理和经验沉淀。

做 AI 平台这件事，最迷人的地方在于：它要求你同时是最乐观的（相信 AI 能做到）和最悲观的（假设一切都会出错）的工程师。乐观让你敢想，悲观让你把底盘做扎实。这 70 篇里，前一半的底气来自乐观，后一半的韧性来自悲观。两者缺一不可。

模型是引擎，工程是底盘和转向。引擎再猛，底盘散架，车还是开不到终点。

希望这 70 篇，能帮你在"AI 平台"这条路上，把底盘做扎实一点。
