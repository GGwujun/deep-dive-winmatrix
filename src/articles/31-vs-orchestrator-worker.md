# WinMatrix vs Anthropic orchestrator-worker：角色优先 vs 大脑优先

> 这是《WinMatrix 开发经验文集》第 31 篇，也是"行业对比与方法论"系列的第一篇。接下来五篇（31-35）不再深挖某一个源码模块，而是把 WinMatrix 的某些设计选择，和业界已知的做法摆在一起对比，讲清楚各自的取舍。这篇聊两种多 Agent 范式：我们选的"角色优先"，和业界常见的"大脑优先"。

做多 Agent 系统，第一个要回答的架构问题是：**多个 Agent 之间，是什么关系？**

这个问题有两种典型答法，代表了两种不同的范式。

一种是 WinMatrix 选的——**角色优先（role-first）**：先定义一组人格化的角色（大福是总指挥、小品是产品、阿码是架构……），每个角色有自己的能力边界、工具权限、记忆空间，Agent 是角色的实例化。

另一种是业界更常见的——姑且叫**大脑优先（brain-first）**：先有一个具备通用能力的"主 Agent"（orchestrator / lead），它动态地把任务拆分、派发给若干子 Agent（worker / sub-agent），子 Agent 完成后把结果汇报回来，主 Agent 再决定下一步。

这两种范式不是非此即彼的对错关系，而是**在不同场景下各有优劣的取舍**。这篇就把它们摆开，讲清楚各自适合什么。

---

## 先把两种范式画清楚

为了便于对比，先用 ASCII 图把两种范式的典型结构画出来（只画结构，不涉及任何外部实现细节）。

**大脑优先（orchestrator-worker）**：

```
         ┌─────────────────────┐
         │   主 Agent（大脑）    │
         │  动态拆分任务、派发   │
         └──┬──────┬──────┬────┘
            │      │      │
       ┌────▼─┐ ┌──▼─┐ ┌─▼────┐
       │worker│ │worker│ │worker│   ← 子 Agent，按任务动态生成
       │  A   │ │  B  │ │  C   │
       └──────┘ └────┘ └──────┘
```

特征：一个主 Agent 是协调中心，子 Agent 是它的"手"。主 Agent 决定"派谁、派什么、怎么汇总"，子 Agent 只管"完成我接到的那一块"。子 Agent 通常没有持久身份——任务来了生成，任务完了解散。

**角色优先（WinMatrix 的做法）**：

```
   ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
   │ 大福   │ │ 小品   │ │ 阿码   │ │ 阿宁   │  ...
   │orchestr│ │product │ │ tech   │ │process │
   │ ator   │ │design  │ │manager │ │manager │
   └───┬────┘ └───┬────┘ └───┬────┘ └───┬────┘
       │          │          │          │
       └──────────┴──────────┴──────────┘
                   │
          role_inbox（持久收件箱）
          协作会话（conversation）
          流程编排（flow_run）
```

特征：多个角色是**平级的、持久存在的**人格化实体，各自有完整的能力定义。它们之间通过收件箱（role_inbox）、协作会话、流程编排来协作。没有一个"全局大脑"动态派发——谁来处理什么，由决策引擎（第 2、10 章）基于角色能力路由决定。

## 第一个分歧：协作的"语义"从哪来

两种范式最根本的分歧，在于**协作的语义是怎么产生的**。

大脑优先里，协作语义是**运行时涌现**的——主 Agent 看到任务，临时决定"这个要拆成三块、分别派给三个 worker"。今天拆成三块，明天同样的任务可能拆成两块。子 Agent 之间有没有协作、协作顺序是什么，完全由主 Agent 当场决定。灵活，但不可预期。

角色优先里，协作语义是**预先定义**的——大福负责启动和协调、小品负责产品、阿码负责技术、阿宁负责跟踪，这些角色的能力边界和职责是写死的（在 agent_config 表里）。用户找大福，就是来启动项目的；找阿码，就是技术问题。角色之间的协作（"阿码评审小品的 PRD"）是一句有明确语义的话，因为两个角色的能力定义都是清晰的。

这两种语义来源，导致了第一个关键差异——**可预期性**。

### 可预期性：用户知道找谁

在企业场景里，可预期性是个被严重低估的刚需。用户（尤其是非技术的业务用户）使用 AI 时，最大的焦虑是"我不知道它会给我干什么"。如果今天问同一个问题它走 A 路径、明天走 B 路径，用户会失去信任。

角色优先天然提升可预期性。用户知道大福是项目总指挥，找他就是启动项目；知道阿码是架构师，找他就是技术问题。**角色的边界就是用户预期的边界**。这种"找对人"的确定性，是大脑优先很难提供的——因为大脑每次可能自己决定派给谁，用户无从预判。

大脑优先的可预期性，得靠其他手段补——比如给主 Agent 严格的 prompt 约束、让它倾向于稳定地拆分同类任务。但这本质上是"用 prompt 约束一个灵活的东西"，远不如"角色定义就是确定的"来得扎实。

### 协作语义的代价

但角色优先的"预先定义语义"是有代价的。

代价一：**灵活性下降**。一个跨领域的请求（比如"帮我从产品到技术到测试全流程搞定"），可能需要在多个角色间接力。角色边界越清晰，跨界就越需要"路由"——决策引擎得判断先找谁、再转给谁。这套路由机制本身不简单（见第 2 篇的渐进式决策引擎）。大脑优先没这个问题——主 Agent 自己决定怎么拆，不受预设角色边界限制。

代价二：**角色膨胀的风险**。业务变化时，是新增一个角色，还是扩展现有角色的技能？这是个持续的产品判断。WinMatrix 有八大角色（orchestrator/process_manager/product_design_manager/tech_manager/quality_manager/sre_manager/architect/external-agent），这个数量是经过取舍的——太少则每个角色太杂、边界模糊；太多则路由复杂、协作链路长。没有银弹。

## 第二个分歧：权限怎么收敛

第二个分歧在权限治理。企业场景里，"谁能干什么"是刚需。

大脑优先里，权限通常是**集中式**的——主 Agent 持有所有工具的访问权，它决定把哪些工具的能力下放给哪个子 Agent。子 Agent 的权限是主 Agent "借"给它的，临时且动态。这种模式灵活，但有一个风险：**主 Agent 本身是一个权限黑洞**——它什么都能干，一旦它的决策被 prompt 注入污染（见第 28 篇安全护栏），整个系统的权限防线就崩了。

角色优先里，权限是**分布式收敛**的——每个角色只绑定自己需要的工具和技能，质量管理员（小质）不需要部署权限，产品经理（小品）不需要写代码权限。这在数据模型上是一张 project_tool_policy 表，按 `project_id × role_id × tool_name × effect(allow|deny)` 精确控制：

```
权限收敛的逻辑：
  小品（product_design_manager）
    ├── 允许：document.write, knowledge.search, ...
    └── 拒绝：workstation.execute, code.commit, ...
  阿码（tech_manager）
    ├── 允许：workstation.execute, code.review, ...
    └── 拒绝：project.archive, ...
```

**角色绑定工具，比"全局工具池 + 运行时判断"安全得多。** 因为权限边界是静态的、可审计的——你一眼就能看出"小品能不能部署代码"，不用去猜"主 Agent 这次会不会把部署权限借出去"。

这个差异的本质是：**角色优先把权限做成"白名单 + 角色隔离"，大脑优先容易滑向"黑名单 + 运行时判断"**。前者默认安全，后者默认开放。在企业 toB 场景，前者是更稳的起点。

## 第三个分歧：协作怎么发生

两种范式里，Agent 之间传递工作的方式也不一样。

大脑优先里，主 Agent 和 worker 之间通常是**函数调用式**的同步协作——主 Agent 调一个 worker，worker 跑完返回结果，主 Agent 继续。这是"请求-响应"模式，适合短链路、强耦合的子任务（"帮我从这段文本里提取实体"）。

角色优先里，角色之间通过**消息驱动**的异步协作——大福把任务投到小品的 role_inbox（持久收件箱），小品有空就处理，处理完再投回大福的收件箱。这是"投递-处理-回执"模式，适合长链路、松耦合的工作流（"大福启动项目 → 小品写 PRD → 阿码评审 → 阿宁跟踪"）。

role_inbox 的设计（第 19 章）是异步协作的基础：

```prisma
// prisma/schema.prisma（role_inbox 模型核心字段）
model role_inbox {
  event_id
  role_id                    ← 投给哪个角色
  conversation_id
  event_type
  payload
  idempotency_key            ← 幂等键
  status                     ← pending/claimed/running/completed/failed
  claim_owner                ← 谁领走了
  claim_expires_at           ← 领走多久会过期（租约）
  retry_count                ← 重试次数
  turn_id                    ← 关联到哪个 Turn
}
```

注意它带 `idempotency_key`（幂等）、`claim_owner` + `claim_expires_at`（租约抢占）、`retry_count`（重试）。这些都是为异步、可靠、可恢复的协作设计的——消息投了没领、领了没处理完、处理完没回执，每种异常都有兜底。

**异步协作比同步协作复杂得多，但它能承载更长链路、更接近真实企业流程的工作。** 同步协作（大脑优先）适合"快速拆解一个技术任务"，异步协作（角色优先）适合"跑完一个从需求到交付的项目"。两者的适用场景不同。

## 第四个分歧：记忆和身份的连续性

最后一个是记忆。这个问题容易被忽略，但它影响"AI 员工"这个概念能不能成立。

大脑优先里，子 Agent 是临时生成的，任务完了解散。它们的记忆通常是**任务级**的——完成这个任务期间记住的东西，任务结束就没了。主 Agent 的记忆是**会话级**的——一次对话里记住的东西。没有哪个 Agent 有跨任务、跨会话的持久身份记忆。

角色优先里，每个角色是持久存在的实体，有自己的**长期记忆**。小品的记忆里积累着"这个项目之前写过的 PRD、用户偏好什么风格、哪些需求被否决过"。这些记忆存在三层（会话层 / 转录层 / 长期索引层，见第 12 章），跨会话、跨任务地沉淀。

```
角色记忆的三层（WinMatrix）：
  会话层：Redis conversation:{id}（最多 50 条）+ PG conversation_histories
  转录层：PG session_transcript（含 tool/thinking trace，LLM 上下文真源）
  长期索引层：PG memory_chunks/memory_files + ES dense_vector
              ↑ 跨会话持久，按 agent_id 员工维隔离
```

**记忆的连续性，是"AI 是工具"和"AI 是员工"的分水岭。** 工具用完即走，没有记忆；员工有履历、有经验积累、有对项目和人的持续认知。如果我们认真对待"数字员工"这个定位（第 10 篇），记忆的连续性就是刚需——而这天然要求角色是持久实体，不是临时 worker。

## 各自适合什么场景

讲了四个分歧，总结一下两种范式各自的适用场景。这不是"谁好谁坏"，而是"什么场景用什么"。

**大脑优先（orchestrator-worker）适合**：

- 开放域、探索性的任务。任务结构不固定，需要主 Agent 动态拆解。
- 短链路、强耦合的子任务。主 Agent 同步调 worker，快速拿结果。
- 单次会话内完成、不需要跨会话记忆的场景。
- 权限治理相对简单、信任主 Agent 的判断就够的场景。
- 典型例子：通用编程助手（"帮我实现这个功能"动态拆成读代码/写代码/跑测试）、研究型助手（"调研这个主题"动态拆成多个子查询）。

**角色优先（role-first）适合**：

- 流程明确、角色边界清晰的 toB 场景。每个角色有稳定的职责定义。
- 长链路、松耦合的工作流。从需求到交付要多角色接力，跨多个会话。
- 权限需要严格收敛、可审计的场景。每个角色只持有最小必要权限。
- 需要跨会话、跨任务的持久记忆和身份连续性的场景。
- 典型例子：企业项目管理（产品/技术/测试/运维多角色协作）、企业流程自动化（按既定流程多步流转）。

**判断标准很简单：如果你的 AI 要嵌入一个"已经有明确分工的真实团队"的工作流，用角色优先；如果你的 AI 要处理"结构不固定的探索性任务"，用大脑优先。** 别反过来——用角色优先去处理开放域探索任务，会被角色边界绑死；用大脑优先去跑企业流程，会因为缺乏持久身份和权限收敛而处处漏风。

## WinMatrix 为什么选角色优先

最后说说我们为什么选角色优先——这不是因为它"更先进"，而是因为 WinMatrix 的定位决定的。

WinMatrix（翠花）的核心定位是"让 AI 成为团队的一员"（第 10 篇）。这个定位一旦认真对待，整个系统就会被推向角色优先：

- "团队成员"意味着有明确职责——所以要预定义角色。
- "团队成员"意味着有持续关系——所以角色要持久存在、要有记忆。
- "团队成员"意味着权限要清晰——所以角色要绑定工具白名单。
- "团队"意味着成员之间有协作——所以要有 role_inbox、协作会话、流程编排。

每一条都是角色优先的自然推论。如果我们的定位是"一个万能助手"，那大脑优先会更合适——但那不是 WinMatrix 要做的事。

### 我们为此付出的代价

诚实地说，角色优先让我们付出了不小的代价：

- **决策引擎的复杂度**。谁来处理什么，得有一套渐进式决策（5 阶段管线）来判断，而不是主 Agent 一句话决定。这套机制的设计和调优投入很大。
- **协作机制的复杂度**。role_inbox、租约、幂等、重试、协作会话三层存储——光"让多个角色可靠地传递工作"就做了一整套基础设施（第 19 章）。
- **角色治理的产品负担**。什么时候加角色、什么时候加技能、角色边界怎么划——这些是持续的产品判断，没有自动化答案。

如果只做单 Agent（大脑优先的简化版），这些复杂度能省掉一大半。所以第 10 篇里那句"如果你只做单 Agent，恭喜你省了一大半的复杂度"是真心的——角色优先的代价就是复杂度，而这个代价只有在"真的需要多角色协作的企业场景"里才值得付。

## 给后来者的几条总结

1. **两种范式不是对错，是取舍**。角色优先和大脑优先各有适用场景，别把某一方当银弹。
2. **角色优先的核心是"预先定义协作语义"**。角色有明确职责、持久身份、收敛权限。可预期性强，但灵活性低。
3. **大脑优先的核心是"运行时涌现协作语义"**。主 Agent 动态拆分派发。灵活，但可预期性弱、权限易成黑洞。
4. **权限模式不同**。角色优先是分布式白名单（每个角色只持必要权限），大脑优先倾向集中式（主 Agent 持全局权限）。企业场景前者更稳。
5. **协作方式不同**。角色优先走异步消息（role_inbox + 租约 + 幂等），适合长链路；大脑优先走同步调用，适合短链路。
6. **记忆连续性是分水岭**。角色优先天然支持跨会话持久记忆（"AI 员工"的履历），大脑优先的记忆通常是任务级/会话级。
7. **判断标准**：嵌入有明确分工的真实团队 → 角色优先；处理结构不固定的探索任务 → 大脑优先。
8. **角色优先的代价是复杂度**。决策引擎、协作机制、角色治理都要投入。只在真的需要多角色协作的企业场景里才值得。

选型没有对错，只有"你的产品定位是什么"。先把定位想清楚，范式自然就定了。最怕的是定位没想清楚就抄一个范式，跑一半发现不对，再迁移——那个代价远大于一开始想清楚。
