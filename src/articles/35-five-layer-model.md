# 企业级 AI 落地的五个层级：从模型到可观测

> 这是《WinMatrix 开发经验文集》第 35 篇，"行业对比与方法论"系列的收尾篇。前面 31-34 分别聊了多 Agent 范式、编码沙箱、决策路由、可观测的取舍。这一篇把它们串起来，用一个"五层模型"讲清楚企业级 AI 平台每一层该选什么、自建还是采购、边界在哪里。

做企业级 AI 平台，最容易犯的错是"一锅炖"——把模型、编排、工具、治理、可观测混在一起谈，分不清哪一层用什么方案、哪一层自建哪一层采购。结果是该采购的自建了（白白投入工程），该自建的采购了（被供应商锁死、改不动）。

业界有一些公开的分层思路（比如有的团队把 Agent 平台分成基础模型、编排、工具、治理、可观测等层），方向是对的——**AI 平台是分层的，每一层有独立的选型和自建边界**。这篇就用一个五层模型，把前面 34 篇讲的所有设计选择归类，讲清楚每一层的取舍。

需要说明的是：这个五层划分是一个回顾性的框架，不是 WinMatrix 一开始就照着设计的。我们是做着做着，回头发现"哦，原来我们的决策都落在这五个层面"。所以这篇文章既是系列的收尾，也是"如果你要从零做一个企业 AI 平台，该按什么框架思考"的指南。

```
├─────────────────────────────────────────────┤
│ 第 3 层：工具与执行（Tools & Execution）      │  ← 这篇 + 第 5/14/15/32 篇
│   工具治理 / 技能 / 编码沙箱 / 工具循环        │
├─────────────────────────────────────────────┤
│ 第 2 层：编排（Orchestration）                │  ← 这篇 + 第 1/2/7/31/33 篇
│   决策引擎 / Turn / 多 Agent 协作 / 流程编排   │
├─────────────────────────────────────────────┤
│ 第 1 层：模型与内核（Model & Kernel）         │  ← 这篇 + 第 3/12 篇

└─────────────────────────────────────────────┘
```

从下往上是"从基础设施到业务支撑"的顺序：第 1 层是模型的接入和内核原语，第 2 层是让模型"会干活"的编排，第 3 层是让 Agent "有工具可用"的执行体系，第 4 层是让一切"安全可控"的治理，第 5 层是让一切"看得见"的可观测。

下面逐层讲。

---

## 第 1 层：模型与内核（Model & Kernel）

**这层管什么**：LLM 的接入（接哪家 provider、怎么路由）、记忆系统、上下文组装、Provider 抽象。

**WinMatrix 的选型**：

- **Provider 抽象自建**。`llmFactory.initProviderRegistry()` 在启动时初始化 provider 注册表（第 28 章），支持多 provider（claude / codex / hermes / openclaw 等），通过 `ILLMClient` 接口统一抽象（`stream()` 流式 + `invokeNonStreaming()` 工具调用，第 14 章）。
- **记忆系统自建**。三层记忆（会话层 / 转录层 / 长期索引层），三区检索（Zone1 当前会话 / Zone2 项目记忆 / Zone3 跨会话），双写 ES + PG（第 12 章）。
- **上下文组装自建**。`MemoryContextBootstrap.injectLongTermMemory()` 每轮自动检索注入，带明确上限（记忆 top-k=5、历史 10、工作上下文 10，第 27 章）。

**build vs buy**：

| 子层 | 选型 | 理由 |
|------|------|------|
| LLM provider 接入 | 自建抽象层 | 多 provider 路由、按 purpose 选模型（如 skill_distill 走 mini）、binding 无密钥设计，这些是业务语义，现成 SDK 满足不了 |
| 向量检索 | 部分用开源（ES） | 用 ES 的 kNN + BM25 做混合检索，不依赖独立向量库（已从 ChromaDB 迁出） |
| 记忆/上下文组装 | 自建 | 记忆的三层结构、三区检索、和员工/项目维度的耦合，是核心业务逻辑，不能外包 |

**这一层的洞察**：模型本身是买的（调 provider API），但"怎么用模型"是自建的。provider 给你的是能力，怎么把能力组装成"有记忆、有上下文、会按 purpose 选模型"的内核，是你自己的工程。这一层别指望 provider 或现成框架帮你做完——它们只给你 `chat()` 接口，剩下的得自己搭。

---

## 第 2 层：编排（Orchestration）

**这层管什么**：决策引擎（消息进来走什么路径）、Turn 执行、多 Agent 协作、流程编排。

**WinMatrix 的选型**：

- **决策引擎自建**。5 阶段渐进式管线（ExactRouter → FusionRouter → QuickAcceptGate → DecisionPlanner → CommitmentDeriver），确定性优先，LLM 兜底（第 2、10 章）。
- **Turn 执行自建**。`TurnRunner` 单轨编排（load → admit → resolveRoute → assembleExecution），三路并行 IO（第 1 章）。
- **多 Agent 协作自建**。角色优先范式，八大数字员工 + role_inbox 持久收件箱 + 协作会话三层存储（第 7、19、31 章）。
- **流程编排自建**。template → template_version → run 三层模型，provides/consumes 显式契约（第 20 章）。

**build vs buy**：

| 子层 | 选型 | 理由 |
|------|------|------|
| 决策引擎 | 自建 | 渐进式（确定性优先 + LLM 兜底）是企业场景必需。全 LLM 图框架（AutoGPT 类）不稳、贵、不可调试（第 33 篇） |
| Turn/执行循环 | 自建 | 工具调用双终止、流式 + 容错、预算控制，这些执行细节和业务深度耦合 |
| 多 Agent 协作 | 自建 | 角色优先范式（第 31 篇）、role_inbox 的幂等/租约/重试，是企业协作的刚需，现成框架不做 |
| 流程编排 | 自建 | provides/consumes 契约校验、指令驱动按需编排、和技能体系深度耦合 |

**这一层的洞察**：编排是整个平台"灵魂"所在，几乎必须自建。现成框架（LangGraph、AutoGPT、Dify 等）的编排哲学和企业的稳定/成本/可调试诉求往往不匹配（第 33 篇详细聊过）。这不是说现成框架没价值——它们适合做原型、探索能力边界——但到了企业生产，编排层基本都得演化成"确定性优先 + LLM 兜底"的渐进式形态，与其后期改造，不如一开始自建。

## 第 3 层：工具与执行（Tools & Execution）

**这层管什么**：工具治理（工具注册、权限、策略）、技能体系、编码沙箱、工具调用循环。

**WinMatrix 的选型**：

- **工具治理自建**。27 个工具域模块，BaseTool 基类统一抽象，`project_tool_policy` 表做项目级 allow/deny，声明式操作授权（declaredOperations）（第 5、14 章）。
- **技能体系自建**。artifact-store 产物模式（不走 bundled），L1/L2/L3 readiness gate，provides/consumes 契约，SkillTrace → SkillExecGuide 蒸馏闭环（第 6、13 章）。
- **编码沙箱自建**。三层镜像（base → engine → component）+ 远程 sandbox-api，4 种引擎自由组合（第 15、32 篇）。
- **工具调用循环自建**。`StreamingToolExecutor` 双终止（iteration + LLM rounds），流式 + 空 args 降级非流式（第 11 章）。

**build vs buy**：

| 子层 | 选型 | 理由 |
|------|------|------|
| 工具治理 | 自建 | 工具和业务深度耦合（27 个域模块都是业务工具），权限要按 project × role × tool 精确控制 |
| 技能体系 | 自建 | 技能是数字员工的能力单元，artifact + 契约 + 治理 + 蒸馏，是企业 AI 的核心资产，不能外包 |
| 编码沙箱 | 自建（有代价） | 三层镜像 + 远程 Pod 的定制力是社区标准（K8s Agent Sandbox 类）给不了的（第 32 篇）。但维护成本高，团队小可考虑社区方案 |
| MCP 接入 | 部分用标准 | MCP 协议本身用社区标准（既是 Server 又是 Consumer），但多租户/白名单/凭证管理自建（第 22 章） |

**这一层的洞察**：工具和技能是企业 AI 的"肌肉"，基本必须自建——因为它们承载的是你的业务能力，没人能替你定义"写 PRD 技能长什么样"。编码沙箱是个例外，它是少数"可以考虑用社区方案"的子层——如果你的沙箱需求不特殊（第 32 篇详细聊过取舍），社区标准的 K8s Sandbox 方案能省一大半工作量。MCP 这类协议层用社区标准，协议之上的业务层（多租户、凭证、白名单）自建。

## 第 4 层：治理（Governance）

**这层管什么**：认证授权、权限模型、幂等设计、审计、安全护栏。

**WinMatrix 的选型**：

- **认证自建**。JWT（HS256，secret ≥32 字符）+ Redis 黑名单，三路 token 提取（第 6 章）。
- **权限双轨自建**。静态矩阵（编译期，60+ PermissionKey）+ 动态 RBAC（DB + Redis 缓存 300s）（第 6 章）。
- **幂等自建**。5 种形态：idempotency_key / attemptNo / claim_token / hash 去重 / partial unique index（第 23 章）。
- **安全护栏多层自建**。认证/授权/输入/执行/基础设施五层防御，声明式操作授权防 prompt 注入（第 28 章）。
- **MCP 多 token 体系自建**。PAT / WMA / WMEC 三类 token，Token Broker 统一路由（第 6 章）。

**build vs buy**：

| 子层 | 选型 | 理由 |
|------|------|------|
| 认证（JWT） | 自建 | 标准 JWT 库 + 自己的黑白名单逻辑，轻量且可控 |
| 权限模型 | 自建 | 双轨（静态矩阵 + 动态 RBAC）是企业 toB 的刚需，现成 RBAC 框架做不了"编译期 + 运行时"双轨 |
| 幂等设计 | 自建 | 5 种幂等形态散落在多个模块，是业务逻辑的一部分，不是独立组件 |
| 审计 | 自建 | 审计日志和执行追踪统一在 ExecutionSpan（第 8 章），不外挂独立审计系统 |
| 安全护栏 | 自建 | 多层防御 + fail-closed + 声明式授权，是业务安全的核心，不能外包 |

**这一层的洞察**：治理层是"企业级"和"玩具"的分水岭。一个没有权限模型、没有幂等、没有审计的系统，demo 再炫也进不了企业。治理层几乎全部自建——不是因为现成方案不好，而是因为治理要和业务深度绑定（"哪个项目的哪个角色能调哪个工具"这种粒度，现成 RBAC 框架表达不了）。这一层的投入往往被低估，但它是企业能否采购你的产品的硬门槛。

## 第 5 层：可观测（Observability）

**这层管什么**：执行追踪、成本归因、悬挂补偿、可观测数据治理。

**WinMatrix 的选型**：

- **执行追踪自建**。ExecutionSpan 是 retire-agent-execution-log 后的 SSOT，span 树 + events 双写 + 三 Sink 路由（第 8、25、34 篇）。
- **成本归因自建**。token 按员工/项目/技能/模型四维归因，基于 span 树回溯（第 29 篇）。
- **悬挂补偿自建**。llmCallWatchdogSweeper 每 10 分钟扫超时调用，补写终态 + 级联 finalize（第 8、36 篇）。
- **可观测数据治理自建**。UnifiedObservabilityRule 决定每个事件类型落 span/log/channel 的组合 + 脱敏策略（第 8 章）。

**build vs buy**：

| 子层 | 选型 | 理由 |
|------|------|------|
| 执行追踪 | 自建 | 可观测 + 业务同库可 JOIN，span 承载业务语义，SSOT（第 34 篇详细聊过） |
| 成本归因 | 自建 | token 归因要按业务维度（员工/技能/项目），provider 账单是平的 |
| 可视化 | 可考虑通用平台 | 这是我们自建里相对薄弱的——主要靠 SQL。混合方案：核心 span 自建，可视化借通用平台 |
| LLM 调用监控 | 可考虑通用平台 | 日常监控和 dashboard 可以借 Langfuse/LangSmith 的现成能力 |

**这一层的洞察**：可观测是少数"可以考虑混合方案"的层（第 34 篇详细聊过）。核心执行追踪自建（SSOT + 业务 JOIN + 精细路由），但可视化和日常监控可以借通用平台省事。这层的自建投入大、回报慢，团队小可以先用通用平台，规模上来再考虑自建核心。

## 把五层放一起看：自建的边界

把五层的 build vs buy 汇总：

```
层             自建度      理由
─────────────────────────────────────────────────
第 1 层 模型    高          模型接入 + 记忆 + 上下文是核心工程
第 2 层 编排    几乎全自建    编排哲学和企业诉求深度绑定
第 3 层 工具    高          工具/技能是业务资产；沙箱可考虑社区方案
第 4 层 治理    几乎全自建    和业务深度耦合，是企业级门槛
第 5 层 可观测  中（可混合）   核心自建，可视化可借通用平台
```

**一个清晰的规律**：越靠近业务的层（编排、工具、治理），越要自建；越靠近基础设施的层（模型 provider、可视化、向量检索），越可以考虑采购或用开源。

这不是"自建就好"——自建意味着工程投入、维护负担、迁移成本。每一层自建前都要问：**这一层的特殊性，值不值得我背自建的代价？** 答案因团队和场景而异。

### 一个常见的误区：全自建

有些团队（尤其是技术实力强的团队）倾向"全自建"——五层全部自己来。这是过度自信。全自建的代价是：

- 工程投入巨大，每个层都从零做起，时间成本高。
- 每一层都要背长期维护负担，团队被基础设施拖累，没法专注业务。
- 错过社区/供应商的持续改进（比如 provider 的新模型、新能力，现成 SDK 跟得比你快）。

WinMatrix 也没有全自建——向量检索用 ES（开源），MCP 协议用社区标准，镜像构建用现成工具链。**自建的是"和业务深度耦合、现成方案满足不了"的部分，其余的能用现成就用现成。**

### 另一个误区：全采购

另一些团队（尤其是非技术驱动的团队）倾向"全采购"——五层全部用现成平台/框架。这同样有问题：

- 编排层和治理层用现成方案，会被供应商锁死，业务变化时改不动。
- 核心能力（工具、技能、记忆）外包，等于把"AI 平台的灵魂"交给了别人。
- 多个供应商拼接，集成成本和对账负担反而比自己做一个还大。

**AI 平台的核心层（编排、工具、治理）是企业的差异化竞争力所在，不能外包。** 外包了，你的 AI 平台就和别人的没区别——而没区别的产品在企业市场是卖不上价的。

## 每一层的"如果只记住一件事"

五层讲完了，每一层浓缩成一句话：

**第 1 层 模型与内核**：模型是买的，"怎么用模型"是自建的。记忆和上下文组装是核心工程，别指望 provider 或现成框架帮你做完。

**第 2 层 编排**：确定性优先于 LLM。决策引擎渐进式（规则优先 + LLM 兜底），LLM 是最后一张牌不是第一张。全 LLM 图在企业场景会被稳定性、成本、可调试性劝退。

**第 3 层 工具与执行**：工具和技能是业务资产，必须自建。技能用 artifact 产物模式，不走硬编码 bundled。沙箱是少数可考虑社区方案的子层。

**第 4 层 治理**：治理是企业级和玩具的分水岭。权限双轨（静态矩阵 + 动态 RBAC）、幂等五形态、多层安全护栏——这些不做，demo 再炫也进不了企业。

**第 5 层 可观测**：可观测数据和业务同库可 JOIN 是自建的核心价值。SSOT（退役散落日志）+ 业务语义 span + 三 Sink 路由。可视化可借通用平台。

## 这个系列想要传递的，最终是一句话

31-35 这五篇行业对比，表面上是"我们 vs 业界"，但真正的主题是一句话——**工程选型的本质是取舍，不是站队**。

- 第 31 篇：角色优先 vs 大脑优先，不是谁对谁错，是看你的 AI 要嵌入有分工的团队（角色优先），还是处理开放探索任务（大脑优先）。
- 第 32 篇：自建沙箱 vs 社区标准，不是谁先进，是看你的沙箱是"给可信 AI 的定制环境"（自建），还是"跑不可信代码的通用底座"（社区）。
- 第 33 篇：渐进式决策 vs 全 LLM 图，不是谁强大，是看你的请求主要是模式化（渐进式），还是探索性（全 LLM）。
- 第 34 篇：自建可观测 vs 通用平台，不是谁更好，是看你需不需要可观测和业务深度关联（需要就自建，不需要就通用）。
- 第 35 篇：五层模型自建 vs 采购，不是越多自建越好，是越靠近业务越自建、越靠近基础设施越采购。

模型是引擎，工程是底盘和转向。引擎再猛，底盘散架，车还是开不到终点。这五层模型，就是企业级 AI 平台的"底盘图纸"——希望它能帮你在"AI 员工"这条路上，把底盘做扎实一点。

---

## 给后来者的几条总结

1. **AI 平台是分层的，五层各有选型**。模型 / 编排 / 工具 / 治理 / 可观测，每一层的 build vs buy 独立决策。
2. **越靠近业务越自建**。编排、工具、治理是差异化竞争力，不能外包。模型 provider、可视化、向量检索能用现成就用现成。
3. **第 1 层：模型是买的，用模型是自建的**。记忆、上下文、provider 抽象是核心工程。
4. **第 2 层：编排几乎全自建**。确定性优先于 LLM，渐进式决策是企业场景的默认选择。
5. **第 3 层：工具技能自建，沙箱可借社区**。工具和技能是业务资产；沙箱是少数可考虑社区方案的子层。
6. **第 4 层：治理是企业级门槛**。权限双轨、幂等五形态、多层护栏，这些不做进不了企业。
7. **第 5 层：可观测核心自建，可视化可借平台**。可观测 + 业务同库可 JOIN 是核心价值，SSOT 消除数据源歧义。
8. **避免全自建和全采购两个极端**。自建和业务深度耦合的部分，采购基础设施和现成能力。选型的本质是取舍，不是站队。

这五层不是死的框架，而是思考的脚手架。你的平台可能多一层少一层、层的划分也可能不同——但"分层思考、每层独立决策 build vs buy"这个方法，是通用的。希望这个脚手架，能帮你在企业级 AI 落地这件事上，少绕几圈。
