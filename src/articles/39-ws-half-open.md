# WebSocket 半断开：连接没断但消息不再来

> 这是《WinMatrix 开发经验文集》第 39 篇。前面三篇讲的都是"后端状态的脏数据"，这一篇回到网络层——一个让所有长连接系统吃过苦头的故障：半断开。TCP 连接看起来是好的、WebSocket 的 `close` 事件没触发、前端以为还连着，但消息早就不通了。讲我们怎么用协议层 ping/pong 检测半开，以及重连时怎么用 `connection:sync` 帧三步防住 terminal 竞态。

第 4 篇讲流式输出时，我提到过半断开是"长连接系统的头号隐形杀手"，并用几段话带过了 ping/pong 的做法。这一篇是它的展开版——因为我们后来发现，半断开的坑远不止"检测到然后断开"这么简单，重连时的状态同步才是真正要命的地方。

先说现象。

---

## 现象：用户说"AI 不理我了"，但服务端看到连接还在

这个故障的用户侧表现极其迷惑：用户在手机上和 AI 聊天，切到微信回了个消息，切回来——AI 不再回复了。输入框能动、发送按钮能点，但消息发出去没有回应。用户以为 AI "卡了"或者"坏了"，怒刷新页面，一切恢复正常。

服务端看日志呢？更迷惑：这个用户的 WebSocket 连接**还在**，`close` 事件没触发，连接状态是 `OPEN`。服务端还在往这个连接推消息（`socket.send` 调用没报错），只是这些消息全部进了黑洞——客户端根本收不到。

这就是 **TCP 半开连接（half-open connection）** 的经典表现。

```
客户端视角:    我还连着啊（socket.readyState = OPEN），但收不到消息
    │
    │  ←── 中间的网络断了（但 TCP 没发现）──→
    │
服务端视角:    连接还在（onclose 没触发），我一直在发消息啊
```

两端都以为连接是好的，但中间的通路早断了。这种状态可以持续很久——如果不主动探测，TCP 层要等到 TCP keepalive 超时（默认 2 小时）才会发现连接没了。2 小时里，用户早就骂骂咧咧走了。

---

## 根因：TCP 半开 + WebSocket 的 close 依赖双向通信

要理解半断开为什么这么难发现，得从 TCP 和 WebSocket 的关系说起。

WebSocket 建立在 TCP 之上。当客户端的网络中断（切后台、进地铁、Wi-Fi 切换），客户端的 TCP 栈可能直接没了，但**不会给服务端发 FIN 包**（FIN 是正常关闭的四次挥手的第一步）。没有 FIN，服务端的 TCP 栈不知道连接断了，应用层的 WebSocket `onclose` 事件自然也不触发。

于是服务端以为连接还在。它继续往这个"看起来 OPEN 的连接"发消息——TCP 层会把这些消息塞进发送缓冲区，缓冲区满了就丢弃或报错，但 **WebSocket 应用层感知不到**（`socket.send` 在缓冲区没满时是同步成功的）。

```
正常关闭:    客户端发 FIN ──→ 服务端 TCP 收到 ──→ 触发 onclose ──→ 清理资源
半断开:      客户端 TCP 没了（没发 FIN）──→ 服务端 TCP 不知道 ──→ onclose 不触发 ──→ 资源泄漏
```

这就是为什么不能依赖 `onclose` 来做半断开的检测——**它根本不会触发**。

很多人第一反应是"用应用层心跳"——服务端每隔几秒发一个心跳消息，客户端收到后回一个，超时就认为断了。但这有个要命的前提：**客户端必须配合**。你得在前端代码里写"收到心跳就回复"的逻辑。而浏览器的 WebSocket API 不直接暴露心跳协议，你得自己在应用消息层实现。前端有个 bug、或者用的是第三方客户端、或者协议版本不一致——心跳就失效了。

我们需要一种**不依赖客户端应用代码配合、在协议层自动完成**的检测手段。

---

## 修复第一层：协议层 ping/pong 检测半开

WebSocket 协议（RFC 6455）在协议层就定义了 ping/pong 控制帧。关键特性是：**浏览器收到协议层的 ping 帧后，会自动回 pong 帧，不需要应用代码介入。** 这是协议规定的义务，不是可选的。

我们就用这个。

```typescript
// interface/api/agents/agentWebSocket.ts（第 391-438 行）
// 服务端原生 ping/pong 半断开检测（浏览器自动响应 ping 帧）
const PING_INTERVAL_MS = 30_000;   // 每 30 秒发一次 ping
const PONG_DEADLINE_MS = 10_000;   // pong 的截止时间是 10 秒
let pongReceived = true;
if (canPing) {
  rawSocket.on?.('pong', () => { pongReceived = true; clearTimeout(pongTimer); });
  pingTimer = setInterval(() => {
    if (!pongReceived) { rawSocket.terminate(); return; }  // 上一轮没收到 pong → 直接终止
    pongReceived = false;
    rawSocket.ping();
    pongTimer = setTimeout(() => { if (!pongReceived) rawSocket.terminate(); }, PONG_DEADLINE_MS);
  }, PING_INTERVAL_MS);
}
```

这段代码看着短，但每个细节都是踩坑后调出来的。

**为什么用 `rawSocket.ping()` 而不是 `socket.send('ping')`？** 因为 `socket.send` 发的是**应用层数据帧**（文本或二进制），客户端的应用代码要自己解析和处理。而 `rawSocket.ping()` 发的是**协议层控制帧**，浏览器 WebSocket 实现会自动响应 pong，应用代码完全无感。这就是"不依赖客户端配合"的关键。

**状态机式的判定（`pongReceived` 标志位）。** 逻辑是：

1. 每轮 ping 前，先检查上一轮的 `pongReceived` 标志。
2. 如果上一轮没收到 pong（标志还是 false），说明客户端已经半断了——直接 `rawSocket.terminate()` 强制关闭。
3. 如果上一轮收到了 pong，把标志重置为 false，发新的 ping。
4. 设一个 10 秒的 pong 截止定时器（`pongTimer`），如果 10 秒内 pong 没回来，也 terminate。

这是一个**两轮才判定**的状态机：第一轮 ping 发出，如果 30 秒后（下一轮开始时）pong 还没回来，或者 10 秒截止到了，才真正 terminate。这样能容忍单次 pong 的轻微延迟（比如网络抖动），避免误杀慢网络。

**为什么是 30 秒 ping + 10 秒截止？** 这是在"早发现"和"不误杀"之间的权衡。30 秒一轮 ping，意味着最坏情况下，一个半断开的连接会在 `30 秒（上一轮尾巴）+ 10 秒（截止）= 40 秒` 内被发现并清理。40 秒对于聊天场景是可以接受的——用户切后台 40 秒后回来重连，体验上就是"稍微等了一下"。如果设得太短（比如 5 秒 ping），慢网络下的正常连接会被误杀，用户频繁遭遇"莫名断开重连"。

**`terminate()` 而不是 `close()`。** `close()` 是优雅关闭（发 close 帧、等对方确认），但半断开的情况下对方已经收不到 close 帧了，`close()` 会卡住。`terminate()` 是底层 socket 直接销毁（RST），不管对方。对半断开的连接，必须用 `terminate()`。

这一层解决的是"发现半断开并清理死连接"。但故事到这里只讲了一半——**连接清掉了，用户重连回来时，怎么把断线期间错过的状态补给他？**

## 修复第二层：connection:sync 重连三步防 terminal 竞态

半断开被检测到、`terminate()` 之后，客户端会感知到连接断了（终于！），触发重连。重连后，客户端要恢复到"断线前"的状态——尤其是那些在断线期间已经结束的对话（terminal 事件）。

这是整个半断开修复里最难的部分。难在哪？难在一个**竞态窗口**。

先看重连同步的实现：

```typescript
// interface/api/agents/ws/connectionSyncHandler.ts（第 35-134 行）
export async function tryHandleConnectionSync(
  message, socket, authenticatedUserId, registerPushForConversation?,
): Promise<boolean> {
  // 重连 sync 帧：
  // 1. 批量鉴权（这个用户对这些会话还有权限吗？）
  // 2. 为授权会话重新注册 push registry（在状态查询之前，避免 terminal 竞态）
  // 3. 批量读 canonical 状态
  // 4. 返回 connection:sync_result
}
```

客户端重连后，发一个 `connection:sync` 帧，带上自己"关心的会话列表"。服务端走四步处理。关键在第 2 步和第 3 步的**顺序**。

### 竞态场景：为什么不能"先读状态再注册 push"

假设我们反过来——先读状态（第 3 步），再注册 push（第 2 步）：

```
时刻 T1: 客户端重连，发 connection:sync
时刻 T2: 服务端读会话状态 ──→ "这个会话还在 running"
时刻 T3: 会话恰好在这时结束了，发布 terminal 事件
         但客户端还没注册 push ──→ terminal 推送没人收 ──→ 丢了
时刻 T4: 服务端注册 push
时刻 T5: 服务端把 T2 读到的"还在 running"返回给客户端
         
结果: 客户端以为会话还在跑，永远等不到结束信号
```

这就是 terminal 竞态：**在"读状态"和"注册 push"之间，恰好发生了 terminal 事件，这个事件既没被"读状态"捕获（读的时候它还没发生），也没被"push"捕获（push 还没注册）。** 它永远地丢了。

用户的表现就是"AI 一直转圈，明明早就回答完了"。

### 正确顺序：先注册 push，再读状态

把第 2 步和第 3 步调过来：

```
时刻 T1: 客户端重连，发 connection:sync
时刻 T2: 服务端为授权会话注册 push ──→ 从现在起，所有事件都会推给客户端
时刻 T3: 会话恰好在这时结束，发布 terminal 事件 ──→ push 已注册 ──→ 客户端收到了 ✓
时刻 T4: 服务端读会话状态 ──→ "这个会话已经 completed"
时刻 T5: 返回 connection:sync_result，含"已 completed"状态

结果: 客户端要么通过 push 收到 terminal（T3 路径），要么通过 sync_result 看到终态（T4 路径）
      两者可能都触发（幂等处理），但绝不会都漏掉
```

**先注册 push 再读状态，保证了"注册窗口期内发生的任何事件都不会被错过"。** 这是一个经典的分布式系统技巧：**注册（订阅）必须在读取之前完成，否则注册和读取之间的窗口期会漏事件。** 消息队列的消费者、Webhook 的注册、文件 watch 的订阅，都是同一个道理。

### 第一步：批量鉴权，鉴权失败绝不注册 push

还有一个安全问题藏在第 1 步里：**重连时要重新鉴权该用户对这些会话的权限。**

```typescript
// 1. 批量鉴权
//    鉴权失败的会话，绝不注册 push
```

为什么重连要重新鉴权？因为权限可能变了。用户可能在断线期间被移出了某个项目、被吊销了某个会话的访问权。如果他重连后还能继续收这个会话的事件，就是越权。

所以鉴权失败的会话，**绝对不能给它注册 push**——否则一个已经没权限的用户，靠着重连就能继续窃听他不该看的事件。这是一个 fail-closed 的设计：权限存疑时，宁可不推，也不能多推。

### sync 帧的另外两个细节

**sync 帧绕过限流（`agentChatLimiter`）。** 正常的对话消息要受并发限制（同一用户同时进行的对话数有上限），但 `connection:sync` 不是一次新的对话，只是恢复已有会话的状态——它不该占用对话并发配额。所以 sync 帧在处理时绕过了 `agentChatLimiter`。

**sync 帧有 schema 版本（`SYNC_SCHEMA_VERSION`）。** 重连协议本身也要演进（比如以后 sync 帧可能带新的字段）。前后端通过 schema 版本协商，避免老客户端用新协议、或新客户端用老协议导致的解析错误。

## 把两层串起来：一次完整的半断开恢复

```
T+0s    客户端切后台，网络断了（TCP 半开）
T+30s   服务端发第 N 轮 ping ──→ 客户端收不到（半断开）
T+40s   pong 截止到，pongReceived 仍为 false ──→ rawSocket.terminate()
T+40s   客户端终于感知到断开，触发重连
T+41s   客户端发 connection:sync 帧（带关心的会话列表）
T+41s   服务端: ① 批量鉴权 ──→ ② 注册 push ──→ ③ 读状态 ──→ ④ 返回 sync_result
T+41s   客户端: 按 sync_result 补齐断线期间错过的状态，继续渲染
T+42s   一切恢复正常
```

从断网到恢复，约 40 秒（ping/pong 检测）+ 重连时间。整个过程中，**用户没有丢失任何状态**——断线期间结束的对话，要么通过 push（重连后注册的）收到 terminal，要么通过 sync_result 看到终态。没有"永远转圈"，没有"丢失结束信号"。

## 教训

**第一，长连接系统的可靠性，80% 取决于你怎么处理"连接看起来在但实际断了"。** 正常的连接建立、消息收发，都是顺境里的直线行驶。半断开才是长连接的"极限工况"——它不报错、不触发 close、静悄悄地吞掉你的消息。**一个没有半断开检测的长连接系统，不是"可能出问题"，是"一定出问题，只是时间问题"。** 尤其在移动端（用户随时切后台、进隧道、切 Wi-Fi），半断开是家常便饭。

**第二，用协议层的机制，而不是应用层的补丁。** 我们用的是 WebSocket 协议层定义的 ping/pong 控制帧，而不是自己发应用层心跳消息。区别在于：协议层的义务由浏览器/客户端运行时自动履行，不依赖应用代码；应用层心跳依赖每个客户端都正确实现。**能用协议层解决的，不要在应用层重新发明轮子。** 协议层是"所有客户端都遵守的契约"，应用层补丁是"希望每个客户端都遵守的愿望"。契约胜过愿望。

**第三，pong 要有截止时间，不能无限等。** 我们给 pong 设了 10 秒截止。如果只是"发了 ping 然后等下一轮 ping 时检查"，最坏要等 30 秒（一个完整周期）。加一个独立的截止定时器，把检测延迟压到 10 秒。**任何"等待对方响应"的逻辑，都要有一个独立的截止时间，而不是依赖下一轮周期来发现。** 无限的等待 = 无限的占用。

**第四，重连同步是"分布式状态机的断点续传"，注册必须在读取之前。** 这是最容易出 bug 的地方。注册 push 和读状态的顺序，差一步就是 terminal 竞态——用户永远等不到结束信号。**凡是"先读状态再订阅"的设计，都要问一句：这两步之间发生的事件，谁来负责？** 如果答不上来，你就有竞态。

**第五，重连要重新鉴权，鉴权失败绝不注册 push。** 权限可能在断线期间变化。一个已经没权限的用户，靠重连还能继续收事件，就是越权漏洞。**重连不是"信任的延续"，是"信任的重新建立"。** 从零开始鉴权，fail-closed。

**第六，terminate() 而不是 close()，对半断开必须用暴力。** `close()` 是优雅关闭，它假设对方还活着、能收到 close 帧并配合。半断开的情况下对方已经死了，`close()` 会卡在等确认。**对不同性质的故障，要用不同的关闭语义。** 正常关闭用 close，异常断开用 terminate。对已经判定死亡的连接讲礼貌，是浪费资源。

## 踩坑系列的小结

这是踩坑扩展系列的第四篇（36-39）。回头看这四个坑，它们有一条暗线：

| 篇 | 坑 | 核心机制 |
|---|---|---|
| 36 | 悬挂的 LLM 调用 | 外部调用必有看门狗代偿补写 end |
| 37 | 孤儿任务 | 启动时 advisory lock 串行收敛 running 残骸 |
| 38 | Schema 漂移 | 启动探测 + 运行识别 + 503 模块降级 |
| 39 | WebSocket 半断开 | 协议层 ping/pong + 重连注册先于读取 |

它们的共性是：**都是"状态在某个环节被卡住了"——LLM 调用卡在 pending、任务卡在 running、API 卡在报错、连接卡在假 OPEN。** 修复它们的核心思路也都是同一个：**不要假设正常路径永远会走完，要有一个独立的机制来检测"卡住"并强制收敛。**

正常路径负责"把事情做对"，代偿机制负责"当正常路径走不完时，把事情收尾"。两者缺一不可。只有正常路径的系统，在顺境里完美无瑕，在逆境里一塌糊涂。加上代偿机制，系统才有了"韧性"——不是不出错，而是出错后能自己爬起来。

这是我们在 WinMatrix 里学到的最重要的一课。
